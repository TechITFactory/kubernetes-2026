Before you start

  • Finish Modules 2–7 first. This lab uses the 3-node kind cluster (kind-lab) and its built-in standard StorageClass.
  • Terminal: bash or zsh — macOS Terminal, Linux, or WSL2 on Windows. Docker must be running: we look inside the kind nodes with docker exec.
  • Go in order, and check every Checkpoint. Volume names, IPs, node choices and ages will differ from yours — that's normal.
  • Something failed? See Troubleshooting at the bottom.
Trainers: pre-load the lab images into the kind cluster before class (MySQL is about 250 MB)

emptyDir: scratch space shared inside one Pod

Slides 3–6, 30~7 min

Goal: Share a folder between two containers, crash one container, then delete the Pod — and see what survives.

Run from: module8-lab/
Creates: shared-volume-pod.yaml
# Create the YAML for a Pod whose two containers share an emptyDir volume
cat > shared-volume-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: shared-volume-pod
spec:
  volumes:
    - name: shared-data
      emptyDir:
        sizeLimit: 64Mi            # scratch space has a budget too
  containers:
    - name: writer
      image: busybox:1.37
      command: ["sh", "-c", "echo 'Hello from Writer!' > /data/message && sleep 3600"]
      volumeMounts:
        - name: shared-data
          mountPath: /data
    - name: reader
      image: busybox:1.37
      # wait for the file instead of hoping the writer was first
      command: ["sh", "-c", "until [ -f /data/message ]; do sleep 1; done; cat /data/message; sleep 3600"]
      volumeMounts:
        - name: shared-data
          mountPath: /data
EOF
Terminal
# Create the shared-volume Pod
kubectl apply -f shared-volume-pod.yaml
# Wait until the Pod is Ready
kubectl wait --for=condition=Ready pod/shared-volume-pod --timeout=60s
# Show the reader container's log to confirm it sees the writer's file
kubectl logs shared-volume-pod -c reader
# Write a new file into the shared volume and list the volume contents
kubectl exec shared-volume-pod -c reader -- sh -c 'echo "saved at $(date +%T)" > /data/note; ls /data'
Expected output
pod/shared-volume-pod created
pod/shared-volume-pod condition met
Hello from Writer!
message
note
Crash the writer container (stop it from the node)
# Find which node the Pod is running on
NODE=$(kubectl get pod shared-volume-pod -o jsonpath='{.spec.nodeName}')
# Get the writer container's ID from the Pod status
CID=$(kubectl get pod shared-volume-pod -o jsonpath='{.status.containerStatuses[?(@.name=="writer")].containerID}' | sed 's#containerd://##')
# Stop the writer container directly on the node to simulate a crash
docker exec $NODE crictl stop $CID >/dev/null
# Wait until Kubernetes has restarted the writer container once
until [ "$(kubectl get pod shared-volume-pod -o jsonpath='{.status.containerStatuses[?(@.name=="writer")].restartCount}')" = 1 ]; do sleep 1; done
# Show the Pod with RESTARTS 1 (the Pod itself survived)
kubectl get pod shared-volume-pod
# Read the note file again to prove it survived the container crash
kubectl exec shared-volume-pod -c writer -- cat /data/note
Expected output
NAME                READY   STATUS    RESTARTS      AGE
shared-volume-pod   2/2     Running   1 (2s ago)    40s
saved at 12:19:15
Now delete the whole Pod and start it again
# Delete the whole Pod immediately
kubectl delete pod shared-volume-pod --now
# Create the same Pod again from the same YAML
kubectl apply -f shared-volume-pod.yaml
# Wait until the new Pod is Ready
kubectl wait --for=condition=Ready pod/shared-volume-pod --timeout=60s
# List the volume to show the note file is gone (emptyDir dies with the Pod)
kubectl exec shared-volume-pod -c writer -- ls /data
Expected output
pod "shared-volume-pod" deleted from default namespace
pod/shared-volume-pod created
pod/shared-volume-pod condition met
message
What just happened
  • Both containers mount the same emptyDir, so the reader sees what the writer wrote. The reader waits for the file instead of hoping the writer started first.
  • A container crash doesn't touch the volume: after the restart, note is still there. The emptyDir belongs to the Pod.
  • Deleting the Pod deletes its emptyDir. The new Pod has only the freshly written message — note is gone.
  • Use emptyDir for caches, temporary files and sharing between containers (Module 6's sidecars). sizeLimit stops one Pod from filling the node's disk. Never keep data you need tomorrow in it.
Checkpoint
note survived the container crash (RESTARTS 1) but not the Pod deletion.
3

hostPath: a folder on the node

Slides 7–8, 30~5 min

Goal: Write nginx logs to a folder on one node and see why that's a trap for application data.

Run from: module8-lab/
Creates: hostpath-pod.yaml
# Create the YAML for a Pod that writes nginx logs to a hostPath folder on one node
cat > hostpath-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: hostpath-volume-pod
spec:
  nodeSelector:
    kubernetes.io/hostname: lab-worker     # pinned, so we know which node to look at
  volumes:
    - name: host-logs
      hostPath:
        path: /var/log/nginx-demo          # a folder on the NODE
        type: DirectoryOrCreate
  containers:
    - name: nginx
      image: nginx:1.28-alpine
      volumeMounts:
        - name: host-logs
          mountPath: /var/log/nginx
EOF
Terminal
# Create the hostPath Pod
kubectl apply -f hostpath-pod.yaml
# Wait until the hostPath Pod is Ready
kubectl wait --for=condition=Ready pod/hostpath-volume-pod --timeout=60s
# Send one request to nginx so it writes an access-log line
kubectl exec hostpath-volume-pod -- wget -qO- http://localhost >/dev/null
# Read the log line on lab-worker, where the Pod ran
echo '--- on lab-worker:'; docker exec lab-worker tail -1 /var/log/nginx-demo/access.log
# Check lab-worker2 to show the folder does not exist there
echo '--- on lab-worker2:'; docker exec lab-worker2 ls /var/log/nginx-demo
# Delete the hostPath Pod
kubectl delete pod hostpath-volume-pod --now
# Show the log files are still on the node after the Pod is gone
echo '--- after the Pod is gone:'; docker exec lab-worker ls /var/log/nginx-demo
Expected output
pod/hostpath-volume-pod created
pod/hostpath-volume-pod condition met
--- on lab-worker:
127.0.0.1 - - [29/Sep/2026:12:19:31 +0000] "GET / HTTP/1.1" 200 615 "-" "Wget" "-"
--- on lab-worker2:
ls: cannot access '/var/log/nginx-demo': No such file or directory
pod "hostpath-volume-pod" deleted from default namespace
--- after the Pod is gone:
access.log
error.log
Tidy the node
# Clean up the leftover log folder on the node
docker exec lab-worker rm -rf /var/log/nginx-demo
What just happened
  • The files live on lab-worker's disk. lab-worker2 has nothing — if the Pod had been scheduled there, it would start with an empty folder.
  • They also outlive the Pod. Nobody cleans them up automatically.
  • hostPath is also a security risk: a Pod that mounts / or the container runtime's socket can take over the node. Most clusters forbid it with Pod Security Admission (Module 9).
  • Good uses: node agents from a DaemonSet (log collectors, monitoring) that must read the node. For app data, use a PersistentVolumeClaim — next.
Checkpoint
The log line is on lab-worker only, and the files stayed after the Pod was deleted.

A claim that waits for its first user

Slides 9–15, 31~5 min

Goal: Ask for 1Gi of storage and see why the claim stays Pending on purpose.

Run from: module8-lab/
Creates: pvc.yaml
# Create the YAML for a 1Gi PersistentVolumeClaim using the default class
cat > pvc.yaml <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: dynamic-pvc
spec:
  storageClassName: standard      # kind's default StorageClass
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
EOF
Terminal
# Create the claim
kubectl apply -f pvc.yaml
# Give the provisioner a moment to react
sleep 5
# Show the claim is Pending (it waits for its first Pod)
kubectl get pvc dynamic-pvc
# Show the WaitForFirstConsumer event that explains why
kubectl describe pvc dynamic-pvc | tail -2
Expected output
persistentvolumeclaim/dynamic-pvc created
NAME          STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
dynamic-pvc   Pending                                      standard       <unset>                 5s
  ----    ------                ----  ----                         -------
  Normal  WaitForFirstConsumer  5s    persistentvolume-controller  waiting for first consumer to be created before binding
What just happened
  • A PersistentVolumeClaim (PVC) is a request: "I need 1Gi, mounted read-write by one node, from class standard".
  • Pending is correct here. The class says volumeBindingMode: WaitForFirstConsumer: don't create the disk until a Pod needs it, so the disk is made on the same node or zone as that Pod.
  • With Immediate binding, the disk could be created in zone A while the Pod is later scheduled to zone B — and the Pod could never start. That's why most cloud classes wait too.
  • Only if a claim stays Pending with a Pod waiting for it is something wrong: read kubectl describe pvc.
Checkpoint
dynamic-pvc is Pending with the event WaitForFirstConsumer.

A Pod uses the claim — the volume appears

Slides 12, 15–17, 31~7 min

Goal: Mount the claim in a Deployment, watch the PersistentVolume get created, and prove the data survives a new Pod.

Run from: module8-lab/
Creates: deployment-with-pvc.yaml
# Create the YAML for a Deployment that mounts the claim
cat > deployment-with-pvc.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-storage
spec:
  replicas: 1
  strategy:
    type: Recreate                  # RWO volume: never run old and new Pod at once
  selector:
    matchLabels:
      app: web-storage
  template:
    metadata:
      labels:
        app: web-storage
    spec:
      containers:
        - name: nginx
          image: nginx:1.28-alpine
          volumeMounts:
            - name: storage-volume
              mountPath: /usr/share/nginx/html
      volumes:
        - name: storage-volume
          persistentVolumeClaim:
            claimName: dynamic-pvc
EOF
Terminal
# Create the Deployment
kubectl apply -f deployment-with-pvc.yaml
# Wait until the rollout finishes
kubectl rollout status deployment/web-storage --timeout=90s
# Show the claim is now Bound
kubectl get pvc dynamic-pvc
# Show the PersistentVolume that was created automatically
kubectl get pv
Expected output
deployment.apps/web-storage created
Waiting for deployment "web-storage" rollout to finish: 0 of 1 updated replicas are available...
deployment "web-storage" successfully rolled out
NAME          STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
dynamic-pvc   Bound    pvc-7080f8cc-c960-4333-9f8c-a81bc1523bcc   1Gi        RWO            standard       <unset>                 10s
NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM                 STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
pvc-7080f8cc-c960-4333-9f8c-a81bc1523bcc   1Gi        RWO            Delete           Bound    default/dynamic-pvc   standard       <unset>                          2s
Write a page, kill the Pod, read it from the new Pod
# Write a web page onto the persistent volume
kubectl exec deploy/web-storage -- sh -c 'echo "<h1>Saved on a PersistentVolume</h1>" > /usr/share/nginx/html/index.html'
# Delete the Pod so the Deployment starts a new one
kubectl delete pod -l app=web-storage --now
# Wait until the replacement Pod is running
kubectl rollout status deployment/web-storage --timeout=90s
# Read the page from the new Pod to prove the data survived
kubectl exec deploy/web-storage -- cat /usr/share/nginx/html/index.html
Expected output
pod "web-storage-7f995ff8f6-4p9zf" deleted from default namespace
deployment "web-storage" successfully rolled out
<h1>Saved on a PersistentVolume</h1>
Where does the data really live?
# Look up the PV name that the claim is bound to
PV=$(kubectl get pvc dynamic-pvc -o jsonpath='{.spec.volumeName}')
# Show the PV's folder path and the node it lives on
kubectl get pv $PV -o jsonpath='path: {.spec.local.path}{.spec.hostPath.path}{"\n"}node: {.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values[0]}{"\n"}'
Expected output
path: /var/local-path-provisioner/pvc-7080f8cc-c960-4333-9f8c-a81bc1523bcc_default_dynamic-pvc
node: lab-worker2
What just happened
  • The Pod asked for the claim; the provisioner created a PersistentVolume (PV) named pvc-… and bound it. Nobody wrote a PV by hand — that's dynamic provisioning.
  • The PVC names its PV, and the PV names its claim (default/dynamic-pvc). describe on either side shows the link (slide 17).
  • The Pod is replaced, the volume is not. The new Pod mounted the same claim and served the saved page.
  • On kind, a volume is a folder on one node, and the PV carries nodeAffinity for that node. Every Pod using it will be scheduled there. On a cloud disk, the same idea applies to a zone.
  • strategy: Recreate: with a single-node volume, the old Pod stops before the new one starts. Safer for data than two Pods writing at once.
Checkpoint
The PVC is Bound, a pvc-… PV exists with policy Delete, and the new Pod shows Saved on a PersistentVolume.

Access modes: ReadWriteOnce vs ReadWriteOncePod

Slides 10, 32~6 min

Goal: Find out what "once" really means — per node or per Pod.

Run from: module8-lab/
Three replicas on one RWO volume
# Scale to 3 replicas to see how ReadWriteOnce behaves
kubectl scale deployment web-storage --replicas=3
# Wait until all replicas are up
kubectl rollout status deployment/web-storage --timeout=90s
# Show that all 3 Pods run on the same node
kubectl get pods -l app=web-storage -o wide | awk '{print $1, $3, $7}'
# Scale back down to 1 replica
kubectl scale deployment web-storage --replicas=1

NAME STATUS NODE
web-storage-7f995ff8f6-bx4ft Running lab-worker2
web-storage-7f995ff8f6-hmmjv Running lab-worker2
web-storage-7f995ff8f6-w9h5w Running lab-worker2
deployment.apps/web-storage scaled
Creates: rwop.yaml — one claim, two Pods
# Create the YAML for a ReadWriteOncePod claim and two Pods that both want it
cat > rwop.yaml <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: single-writer
spec:
  accessModes:
    - ReadWriteOncePod            # exactly one Pod in the whole cluster may use it
  resources:
    requests:
      storage: 1Gi
---
apiVersion: v1
kind: Pod
metadata:
  name: writer-1
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: single-writer
---
apiVersion: v1
kind: Pod
metadata:
  name: writer-2
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: single-writer
EOF
Terminal
# Create the claim and both Pods
kubectl apply -f rwop.yaml
# Give the scheduler time to place the Pods
sleep 15
# Show writer-1 is Running and writer-2 is Pending
kubectl get pods writer-1 writer-2 -o wide | awk '{print $1, $3, $7}'
# Show the scheduling event that explains why writer-2 waits
kubectl get events --field-selector involvedObject.name=writer-2,reason=FailedScheduling -o jsonpath='{.items[-1:].message}{"\n"}'
Expected output
persistentvolumeclaim/single-writer created
pod/writer-1 created
pod/writer-2 created
NAME STATUS NODE
writer-1 Running lab-worker
writer-2 Pending <none>
0/3 nodes are available: 1 node(s) had untolerated taint(s), 2 node(s) unavailable due to PersistentVolumeClaim with ReadWriteOncePod access mode already in-use by another pod. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.
Tidy up
# Delete both Pods
kubectl delete pod writer-1 writer-2 --now
# Delete the ReadWriteOncePod claim
kubectl delete pvc single-writer
ModeShortWho may mount it read-write
ReadWriteOnceRWOPods on one node — any number of them
ReadWriteOncePodRWOPexactly one Pod in the cluster (stable since v1.29)
ReadOnlyManyROXmany nodes, read-only
ReadWriteManyRWXmany nodes read-write — needs shared storage like NFS, EFS, Azure Files, CephFS
What just happened
  • Surprise for most people: RWO means one node, not one Pod. All three replicas landed on lab-worker2 and shared the volume. Two processes writing the same files is how data gets corrupted.
  • RWOP is the real "one writer" guarantee. The second Pod waits with a clear message instead of corrupting data.
  • rwop.yaml has no storageClassName, so it got the default class standard.
  • The backend decides which modes are possible. A cloud block disk can't do RWX; ask for it and the claim stays Pending (slide 38).
Checkpoint
Three RWO replicas on one node; with RWOP, writer-2 is Pending.

Reclaim policy Delete: the claim takes the data with it

Slides 18, 32~3 min

Goal: Delete the app and its claim, and watch the volume and its data disappear.

Run from: module8-lab/
Terminal
# Save the PV name behind the claim
PV=$(kubectl get pvc dynamic-pvc -o jsonpath='{.spec.volumeName}')
# Save the node that holds the PV's folder
NODE=$(kubectl get pv $PV -o jsonpath='{.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values[0]}')
# Delete the Deployment (the Pod must go before the claim)
kubectl delete deployment web-storage
# Wait until the Pod is fully gone
kubectl wait --for=delete pod -l app=web-storage --timeout=60s
# Delete the claim (reclaim policy Delete will remove the volume)
kubectl delete pvc dynamic-pvc
# Give the controller a moment to clean up
sleep 5
# Show the PV is NotFound — it was deleted with the claim
kubectl get pv $PV
# List the node's provisioner folder to show the data is gone
docker exec $NODE ls /var/local-path-provisioner/
Expected output
deployment.apps "web-storage" deleted from default namespace
persistentvolumeclaim "dynamic-pvc" deleted from default namespace
Error from server (NotFound): persistentvolumes "pvc-7080f8cc-c960-4333-9f8c-a81bc1523bcc" not found
What just happened
  • The class standard has reclaimPolicy: Delete. Deleting the claim deleted the PV and the folder on the node — the last ls printed nothing.
  • Delete is the usual default for dynamic classes. It's tidy, and it's exactly how people lose data by running kubectl delete pvc or deleting a namespace.
  • The Pod had to go first. A claim that's still in use is protected: kubectl delete pvc would wait until the Pod is gone (kubernetes.io/pvc-protection).
Checkpoint
The PV is NotFound and the node's folder is empty.

Reclaim policy Retain — and getting the data back

Slides 13, 18, 21, 32~9 min

Goal: Create a class that keeps volumes, delete a claim by mistake, and recover the data with a new claim.

Run from: module8-lab/
Creates: retain-sc.yaml
# Create the YAML for a StorageClass with reclaimPolicy Retain
cat > retain-sc.yaml <<'EOF'
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: keep-data
provisioner: rancher.io/local-path        # same driver as "standard"
reclaimPolicy: Retain                      # keep the volume when the claim is deleted
volumeBindingMode: WaitForFirstConsumer
EOF
Creates: important-data.yaml — a claim and a Pod that writes an invoice
# Create the YAML for a claim and a Pod that writes an invoice file
cat > important-data.yaml <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: invoices
spec:
  storageClassName: keep-data
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
---
apiVersion: v1
kind: Pod
metadata:
  name: invoice-writer
spec:
  containers:

      volumeMounts:
        - name: data
          mountPath: /data
  volumes:

EOF

Troubleshooting

A PVC stays Pending
No Pod uses it yet and the class is WaitForFirstConsumer — that's normal (Step 4). With a Pod waiting: kubectl describe pvc <name> — wrong storageClassName, a provisioner that isn't running, or an access mode the backend can't do.
A Pod stays Pending with volume node affinity conflict
Its local volume lives on another node, and that node is full or tainted. Free the node, or delete the claim if the data isn't needed.
kubectl delete pvc hangs
A Pod still uses the claim (pvc-protection). Delete or scale down the Pod first (Step 7).
A new claim with volumeName stays Pending
The PV is still Released — remove its claimRef first — or the class, size or access mode don't match the PV (Step 8).
mysql Pods stay 0/1 for a long time
First start initializes the database (20–40 s per replica). Check kubectl logs mysql-0. OOMKilled → raise the memory limit.
ERROR 1045 (28000): Access denied for user 'root'
The claim already holds a database created with another password. MySQL only reads MYSQL_ROOT_PASSWORD on first start. Delete the old claims (Step 16) or use the old password.
ErrImagePull for site-content:v1
The image only exists on your machine. Load it into kind (Step 14) and keep pullPolicy: IfNotPresent.
kind load fails with ctr: content digest sha256:… not found
Docker 29 keeps images in its containerd image store: it downloads only your platform, but docker save still lists all of them, and kind's import looks for every one. Save just your platform and load the archive — that's what the pre-load commands at the top of this page do: docker save --platform "$(docker version --format '{{.Server.Os}}/{{.Server.Arch}}')" -o image.tar IMAGE then kind load image-archive image.tar --name lab. Images you built yourself (like module1-demo-api) load fine with kind load docker-image.
ERROR: unknown containerd config version: 4 from kind
Your kind binary is older than the node image. Install kind v0.33 or newer (Module 2, Step 1) and run kind version to check.
