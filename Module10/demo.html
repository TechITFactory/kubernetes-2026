kubectl get gatewayclass

What just happened
  • An Ingress object is only a set of routing rules. Something must read those rules and actually move traffic: the Ingress controller. Kubernetes doesn't ship one (slide 7).
  • Slide 8 enables the controller with minikube addons enable ingress. That's for minikube. On our kind cluster, cloud-provider-kind — the same tool that gave us LoadBalancer IPs in Module 4 — is also an Ingress and a Gateway API controller.
  • The IngressClass names a controller. Ours is cloud-provider-kind, marked as the cluster default. Every Ingress points at a class with ingressClassName.
  • Why not ingress-nginx, the one in most old tutorials? It was retired on March 24, 2026: no more releases, no more security fixes. New clusters pick a maintained controller — or Gateway API (Part D).
Checkpoint

Two apps behind two Services

Slides 3, 5, 33~5 min

Goal: Deploy a web app and an api app. Each one answers with its own name, the Pod that served it, and the path it received.

Run from: module10-lab/
Creates: echo-config.yaml — a tiny nginx config that echoes the request
cat > echo-config.yaml <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: echo-config
data:
  default.conf.template: |       # nginx fills ${APP_NAME} in at start-up
    server {
      listen 80;
      location / {
        default_type text/plain;
        return 200 "${APP_NAME} | pod=$hostname | path=$request_uri\n";
      }
    }
EOF
Creates: web.yaml — Deployment + Service
cat > web.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.29-alpine
          env:
            - name: APP_NAME            # the only line that differs between the two apps
              value: web
          ports:
            - containerPort: 80
          volumeMounts:
            - name: config
              mountPath: /etc/nginx/templates
      volumes:
        - name: config
          configMap:
            name: echo-config
---
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
EOF
Creates: api.yaml — the same app, renamed
sed 's/web/api/g' web.yaml > api.yaml
grep -E 'name:|value:' api.yaml
Expected output
  name: api
            - name: nginx
            - name: APP_NAME            # the only line that differs between the two apps
              value: api
            - name: config
        - name: config
            name: echo-config
  name: api-service
Deploy and test inside the cluster
kubectl apply -f echo-config.yaml -f web.yaml -f api.yaml
kubectl rollout status deploy/web --timeout=90s
kubectl rollout status deploy/api --timeout=90s
sleep 2   # give kube-proxy a moment to program the new Services
kubectl exec deploy/web -- curl -s api-service/hello
kubectl exec deploy/api -- curl -s web-service/hello
Expected output
configmap/echo-config created
deployment.apps/web created
service/web-service created
deployment.apps/api created
service/api-service created
deployment "web" successfully rolled out
deployment "api" successfully rolled out
api | pod=api-6c7f8b9d4-2xkqp | path=/hello
web | pod=web-5d8f7c6b9-7lmnq | path=/hello
What just happened
  • Two ClusterIP Services — web-service and api-service. They work inside the cluster only (slide 3). Users outside can't reach them yet.
  • The official nginx image fills environment variables into files from /etc/nginx/templates at start-up. One ConfigMap, two apps: only APP_NAME differs.
  • Each answer shows which app, which Pod and which path arrived. That makes every routing decision in this lab visible.
Checkpoint
api | pod=api-… and web | pod=web-… — both apps answer.

Ingress: one entry point, path-based routing

Slides 4–7, 9–10, 33~7 min

Goal: Send /api to the api app and everything else to the web app, through one IP.

Run from: module10-lab/
Creates: ingress.yaml
cat > ingress.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-routing
spec:
  ingressClassName: cloud-provider-kind   # which controller should handle this
  rules:
    - host: example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80
EOF
Apply and wait for an address
kubectl apply -f ingress.yaml
until kubectl get ingress web-routing -o jsonpath='{..ip}' | grep -q .; do sleep 2; done
kubectl get ingress web-routing
IP=$(kubectl get ingress web-routing -o jsonpath='{..ip}')
echo "Ingress IP: $IP"
Expected output
ingress.networking.k8s.io/web-routing created
NAME          CLASS                 HOSTS         ADDRESS      PORTS   AGE
web-routing   cloud-provider-kind   example.com   172.19.0.5   80      12s
Ingress IP: 172.19.0.5
Send requests through the Ingress
kcurl() { docker exec lab-control-plane curl -s "$@"; }   # curl from inside kind's network
for path in / /api /api/users /apix; do kcurl -H "Host: example.com" http://$IP$path; done
kcurl -o /dev/null -w "other host -> %{http_code}\n" -H "Host: other.com" http://$IP/
Expected output
web | pod=web-5d8f7c6b9-7lmnq | path=/
api | pod=api-6c7f8b9d4-2xkqp | path=/api
api | pod=api-6c7f8b9d4-9zr4t | path=/api/users
web | pod=web-5d8f7c6b9-v8w2c | path=/apix
other host -> 404
Note: If you open a new terminal later, run the kcurl() … line and the IP=… line again.
What did the controller build?
kubectl describe ingress web-routing | sed -n '/Rules:/,/Annotations/p'
kubectl get gateway,httproute
Expected output
Rules:
  Host         Path  Backends
  ----         ----  --------
  example.com  
               /api   api-service:80 (10.244.2.4:80,10.244.1.3:80)
               /      web-service:80 (10.244.1.2:80,10.244.2.3:80)
Annotations:   <none>
NAME                                                     CLASS                 ADDRESS      PROGRAMMED   AGE
gateway.gateway.networking.k8s.io/kind-ingress-gateway   cloud-provider-kind   172.19.0.5   True         2m
NAME                                                        HOSTNAMES         AGE
httproute.gateway.networking.k8s.io/web-routing-a379a6f6ee   ["example.com"]   12s
What just happened
  • Ingress works at Layer 7 (slide 6): it reads the HTTP Host header and the path, then picks a Service. The Service still picks the Pod (slide 5).
  • pathType: Prefix matches whole path segments: /api/users → api, but /apix → web. It is not a plain string prefix.
  • The host is example.com. Any other Host gets 404 — no rule matched. That's why we send -H "Host: …": we don't own example.com's DNS.
  • Slide 10 showed ADDRESS 192.0.2.20 and CLASS nginx — made-up values. Yours is a real IP from kind's Docker network.
  • Look at the last command: cloud-provider-kind turned your Ingress into a Gateway plus an HTTPRoute. Gateway API is where Ingress is heading — you'll write those yourself in Part D.
  • We call the IP from a kind node (kcurl) because Docker Desktop on macOS/Windows can't reach container IPs. On Linux, plain curl from your laptop works too.
Checkpoint
/api and /api/users → api, / and /apix → web, other host → 404.
4

Host-based routing

Slides 11, 33~4 min

Goal: Route by hostname instead: web.local → web, api.local → api.

Run from: module10-lab/
Creates: ingress-hosts.yaml
cat > ingress-hosts.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: host-routing
spec:
  ingressClassName: cloud-provider-kind
  rules:
    - host: web.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80
    - host: api.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80
EOF
Apply and test
kubectl apply -f ingress-hosts.yaml
sleep 5
kubectl get ingress
for h in web.local api.local; do kcurl -H "Host: $h" http://$IP/hello; done
kcurl --resolve api.local:80:$IP http://api.local/orders
Expected output
ingress.networking.k8s.io/host-routing created
NAME           CLASS                 HOSTS                 ADDRESS      PORTS   AGE
host-routing   cloud-provider-kind   web.local,api.local   172.19.0.5   80      5s
web-routing    cloud-provider-kind   example.com           172.19.0.5   80      3m
web | pod=web-5d8f7c6b9-7lmnq | path=/hello
api | pod=api-6c7f8b9d4-2xkqp | path=/hello
api | pod=api-6c7f8b9d4-9zr4t | path=/orders
What just happened
  • Same IP, same port 80 — the Host header decides. This is how one load balancer serves many websites.
  • Both Ingresses share one address: the controller merges them. In a real company, many teams each write their own Ingress for their own hostnames.
  • --resolve api.local:80:$IP makes curl act as if DNS said api.local = $IP. In production, a DNS record points your hostnames at the Ingress IP.
  • Path or host? Use path when one site has parts (/api, /shop). Use host when each app has its own name (api.company.com).
Checkpoint
web.local → web, api.local → api, on the same IP.

TLS termination at the Ingress

Slides 4, 6, 34~6 min

Goal: Serve https://example.com with a certificate, and let the Ingress decrypt traffic before it reaches the Pods.

Run from: module10-lab/
A self-signed certificate, stored as a TLS Secret, used by the Ingress
openssl req -x509 -nodes -newkey rsa:2048 -days 30 \
  -keyout tls.key -out tls.crt \
  -subj "/CN=example.com" -addext "subjectAltName=DNS:example.com"
kubectl create secret tls example-tls --cert=tls.crt --key=tls.key
kubectl patch ingress web-routing --type=merge \
  -p '{"spec":{"tls":[{"hosts":["example.com"],"secretName":"example-tls"}]}}'
sleep 5
kubectl get ingress web-routing
Expected output
secret/example-tls created
ingress.networking.k8s.io/web-routing patched
NAME          CLASS                 HOSTS         ADDRESS      PORTS     AGE
web-routing   cloud-provider-kind   example.com   172.19.0.5   80, 443   4m
HTTPS — first trusting our certificate, then without it
docker exec -i lab-control-plane curl -s --cacert /dev/stdin \
  --resolve example.com:443:$IP https://example.com/api < tls.crt
kcurl --resolve example.com:443:$IP https://example.com/api; echo "exit code: $?"
Expected output
api | pod=api-6c7f8b9d4-2xkqp | path=/api
exit code: 60
What just happened
  • TLS termination: the Ingress holds the certificate and decrypts HTTPS. Pods receive plain HTTP and never touch the private key.
  • The certificate and key live in a Secret of type kubernetes.io/tls (Module 6). The Ingress tls: block says which hosts use which Secret.
  • With --cacert we tell curl to trust our certificate → 200. Without it, curl refuses (exit code 60: certificate not trusted). That's exactly what browsers do with self-signed certificates.
  • In production, cert-manager gets free certificates from Let's Encrypt and renews them before they expire. The Ingress side stays the same: a tls: block and a Secret name.
Checkpoint
PORTS shows 80, 443, the trusted HTTPS call returns api, and the untrusted one ends with exit code 60.

What just happened
  • By default every Pod can connect to every other Pod, in every namespace. Easy to start with — and one hacked Pod can reach your database (slide 12).

  • kind's plugin, kindnet, has a built-in policy engine, kube-network-policies — the log line proves it's running. On EKS, GKE and AKS you turn on policy support (Calico, Cilium, or the cloud's own).
  • We use nginx:1.29-alpine for every Pod because it has curl inside.

7

Allow only frontend → backend

Slides 13–15, 35~7 min

Goal: Protect the backend so that only Pods labelled app=frontend, in the same namespace, can reach it on port 80.

Run from: module10-lab/
Creates: allow-frontend-to-backend.yaml
cat > allow-frontend-to-backend.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: np-lab
spec:
  podSelector:              # WHO is protected: the backend Pods
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:                 # WHO may connect: Pods labelled app=frontend (same namespace)
        - podSelector:
            matchLabels:
              app: frontend
      ports:                # on WHICH port
        - protocol: TCP
          port: 80
EOF
Apply and test again
kubectl apply -f allow-frontend-to-backend.yaml
sleep 3
for p in frontend test-pod; do kubectl exec -n np-lab $p -- curl -s -m 3 -o /dev/null -w "$p -> %{http_code}\n" backend-service; done
Expected output
networkpolicy.networking.k8s.io/allow-frontend-to-backend created
frontend -> 200
test-pod -> 000
command terminated with exit code 28
Note: Exit code 28 means curl gave up after 3 seconds: the packets were dropped. Some network plugins reject at once instead — then you see exit code 7. Both mean blocked.
Labels are identity: give test-pod the frontend label
kubectl label pod test-pod -n np-lab app=frontend --overwrite
sleep 3
for p in test-pod; do kubectl exec -n np-lab $p -- curl -s -m 3 -o /dev/null -w "$p -> %{http_code}\n" backend-service; done
kubectl label pod test-pod -n np-lab app=test --overwrite
Expected output
pod/test-pod labeled
test-pod -> 200
pod/test-pod labeled
Same label, different namespace
kubectl create namespace other
kubectl run frontend -n other --image=nginx:1.29-alpine -l app=frontend
kubectl wait -n other --for=condition=Ready pod/frontend --timeout=60s
kubectl exec -n other frontend -- curl -s -m 3 -o /dev/null -w "other/frontend -> %{http_code}\n" backend-service.np-lab
Expected output
namespace/other created
pod/frontend created
pod/frontend condition met
other/frontend -> 000
command terminated with exit code 28
What just happened
  • Read the policy like a sentence (slide 15): protect Pods with app=backend, allow Pods with app=frontend, on TCP port 80. Anything else is dropped.
  • Once any policy selects a Pod for Ingress, that Pod is isolated: only traffic some policy allows gets in. Policies only add permissions — like RBAC, there's no "deny" rule.
  • Relabelling test-pod let it in. The network trusts labels, so who may set labels matters. That's one more reason to keep RBAC tight (Module 9).
  • podSelector alone means "Pods in this namespace". The frontend in other has the right label but was blocked. To allow another namespace, add a namespaceSelector (Step 8 shows one).
Checkpoint
frontend 200; test-pod blocked until relabelled; other/frontend blocked.

Default deny, the DNS trap, and egress

Slides 16–17, 36~10 min

Goal: Lock the whole namespace down in both directions, see DNS break, and open only what the app needs.

Run from: module10-lab/
Creates: default-deny.yaml
cat > default-deny.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: np-lab
spec:
  podSelector: {}           # empty = every Pod in the namespace
  policyTypes:
    - Ingress               # nothing may come in...
    - Egress                # ...and nothing may go out, unless another policy allows it
EOF
Deny everything — even the allowed frontend breaks
kubectl apply -f default-deny.yaml
sleep 3
for p in frontend; do kubectl exec -n np-lab $p -- curl -s -m 3 -o /dev/null -w "$p -> %{http_code}\n" backend-service; done
kubectl exec -n np-lab frontend -- nslookup -timeout=2 backend-service
Expected output
networkpolicy.networking.k8s.io/default-deny-all created
frontend -> 000

;; connection timed out; no servers could be reached

command terminated with exit code 1
Creates: allow-dns.yaml
cat > allow-dns.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: np-lab
spec:
  podSelector: {}
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:          # in kube-system...
            matchLabels:
              kubernetes.io/metadata.name: kube-system
          podSelector:                # ...AND labelled k8s-app=kube-dns (one list item = AND)
            matchLabels:
              k8s-app: kube-dns
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
EOF

What just happened
  • podSelector: {} with both policy types is the default deny: every Pod in the namespace is isolated both ways. Real security teams start here, then allow each path on purpose.
  • The DNS trap: after denying egress, the first thing to break is name lookup. The Pod can't ask CoreDNS where backend-service is. Always allow DNS (UDP and TCP 53) to kube-dns in kube-system.
  • In allow-dns.yaml, namespaceSelector and podSelector are in one list item, so both must match (AND). Put a - before podSelector and they become two items (OR) — then any Pod labelled k8s-app=kube-dns in any namespace would match. A classic mistake.
  • A connection needs two yeses: egress allowed at the source (frontend-egress) and ingress allowed at the destination (allow-frontend-to-backend).
  • The frontend still can't reach web-service in default: it isn't on the list. If an attacker takes over the frontend, they can't wander around the cluster.

Gateway API: Gateway + HTTPRoute

Slides 29, 31, 39~8 min

Goal: Build your own Gateway, then route by path and header and split traffic 80/20.

Run from: module10-lab/
Creates: gateway.yaml — owned by the platform team
cat > gateway.yaml <<'EOF'
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shop-gateway
spec:
  gatewayClassName: cloud-provider-kind     # the implementation (like ingressClassName)
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: Selector                    # only namespaces the platform team labels
          selector:
            matchLabels:
              shop-gateway-access: "true"
EOF
Creates: shop-route.yaml — owned by the app team
cat > shop-route.yaml <<'EOF'
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: shop-route
spec:
  parentRefs:
    - name: shop-gateway
  hostnames:
    - shop.local
  rules:
    - matches:                              # rule 1: /api... goes to api
        - path:
            type: PathPrefix
            value: /api
      backendRefs:
        - name: api-service
          port: 80
    - matches:                              # rule 2: testers send a header to reach api
        - headers:
            - name: x-canary
              value: "true"
      backendRefs:
        - name: api-service
          port: 80
    - backendRefs:                          # rule 3: everything else, split 80/20
        - name: web-service
          port: 80
          weight: 80
        - name: api-service
          port: 80
          weight: 20
EOF
Apply and wait until the Gateway is programmed
kubectl label namespace default shop-gateway-access=true
kubectl apply -f gateway.yaml -f shop-route.yaml
kubectl wait --for=condition=Programmed gateway/shop-gateway --timeout=120s
kubectl get gateway shop-gateway
kubectl get httproute shop-route -o jsonpath='{range .status.parents[0].conditions[*]}{.type}={.status}  {end}'; echo
GW=$(kubectl get gateway shop-gateway -o jsonpath='{.status.addresses[0].value}')

What just happened
  • Gateway API splits one Ingress into roles (slide 31): the GatewayClass (the implementation), the Gateway (a listener with an IP, run by the platform team) and HTTPRoutes (rules, written by app teams).
  • Things Ingress could only do with controller-specific annotations are standard here: header matching, and weights for canary releases. The same YAML works on any conformant implementation.

Troubleshooting

Ingress ADDRESS stays empty
No controller is handling it. Check kubectl get ingressclass, that ingressClassName matches, and that cloud-provider-kind is running in terminal 2 (Step 1).
Ingress or Gateway answers 404
No rule matched. Check the Host header (-H "Host: example.com") and the path. pathType: Prefix matches whole segments: /apix doesn't match /api (Step 3).
curl: (60) SSL certificate problem
curl doesn't trust the self-signed certificate. Pass it with --cacert (Step 5), or use a real certificate from cert-manager + Let's Encrypt.
A NetworkPolicy is applied but traffic still flows
The network plugin isn't enforcing it. Check kubectl -n kube-system logs ds/kindnet | grep -i -E 'network-policies|nftables'. Old kind versions had no policy support — use kind v0.33 or newer (Module 2). kindnet also needs the nfnetlink_queue kernel module; if the logs show nftables errors, run sudo modprobe nfnetlink_queue on the Docker host, or install Calico.
Everything broke after a default-deny policy
Egress is denied, so DNS is too. Apply allow-dns.yaml (Step 8). Remember that a connection needs egress allowed at the source and ingress allowed at the destination.
helm: command not found, or helm version shows v3
Install Helm 4 (Step 9). Helm 3 runs most of this lab, but server-side apply by default (the APPLY_METHOD line in Step 10) is new in Helm 4.
Error: INSTALLATION FAILED: cannot re-use a name that is still in use
A release with that name already exists in the namespace. Use helm upgrade, or helm uninstall it first. helm list -A shows every release.
An upgrade lost your settings
You ran helm upgrade without your -f files (Step 11). Roll back with helm rollback <release> <good-revision>, and always pass the same values files.
helm upgrade or install times out with context deadline exceeded
The Pods never became ready. Run kubectl get pods -n helm-lab and describe the failing Pod — usually an image pull or a bad value.
An HTTPRoute shows Accepted=False (NotAllowedByListeners)
The Gateway's allowedRoutes doesn't include that namespace. Label it: kubectl label namespace <ns> shop-gateway-access=true (Step 15). The status can take a few seconds to update.
kind load fails with ctr: content digest sha256:… not found
Docker 29 keeps images in its containerd image store: it downloads only your platform, but docker save still lists all of them, and kind's import looks for every one. Save just your platform and load the archive — that's what the pre-load commands at the top of this page do: docker save --platform "$(docker version --format '{{.Server.Os}}/{{.Server.Arch}}')" -o image.tar IMAGE then kind load image-archive image.tar --name lab. Images you built yourself (like module1-demo-api) load fine with kind load docker-image.
ERROR: unknown containerd config version: 4 from kind
Your kind binary is older than the node image. Install kind v0.33 or newer (Module 2, Step 1) and run kind version to check.
