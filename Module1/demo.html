Run your first container (foreground, then detached)

Slides 8, 12~4 min

Goal: See the difference between a container that holds your terminal and one that runs in the background.

Run from: module1-lab/
1. Foreground — this takes over your terminal
docker run --name web-fg -p 8080:80 nginx:1.28-alpine

You will see nginx start-up logs. Your terminal is now busy. Press Ctrl + C to stop it, then remove it:

Terminal
docker rm web-fg
2. Detached — runs in the background
docker run -d --name web -p 8080:80 nginx:1.28-alpine
docker ps
curl -s http://localhost:8080 | grep title
Expected output
NAMES     IMAGE               STATUS         PORTS
web       nginx:1.28-alpine   Up 2 seconds   0.0.0.0:8080->80/tcp
<title>Welcome to nginx!</title>
What just happened
  • -d (detached) gives you your terminal back.
  • --name web gives the container a name we can use in every later command.
  • -p 8080:80 means host port 8080 → container port 80. Host first, container second.
Note: On Windows PowerShell use curl.exe, or just open http://localhost:8080 in your browser.
Checkpoint
http://localhost:8080 shows Welcome to nginx!

created

paused

Inspect and debug like an operator

Slides 11, 23~4 min

Goal: Get answers from metadata before you ever open a shell.

Run from: module1-lab/
Terminal
docker inspect web | head -30
docker inspect -f '{{.Config.Image}}' web
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' web
Expected output
[
    {
        "Id": "21017624e331...",
        ...
nginx:1.28-alpine
172.17.0.2
Terminal
docker stats web --no-stream
docker top web
docker port web
Expected output
NAME      CPU %     MEM USAGE / LIMIT
web       0.00%     4.855MiB / 15.72GiB

UID    PID    ...   CMD
root   1659   ...   nginx: master process nginx -g daemon off;
...    1707   ...   nginx: worker process

80/tcp -> 0.0.0.0:8080
Handy listing shortcuts
docker ps -q
docker ps --filter "name=web"
What just happened
  • inspect is the full truth about a container, as JSON. -f pulls out one field.
  • stats = live CPU and memory. top = processes inside. port = published ports.
  • ps -q prints IDs only (useful in scripts). --filter searches by name.
Note: Older tutorials use {{.NetworkSettings.IPAddress}}. That shortcut was removed in newer Docker versions — use the range .NetworkSettings.Networks form shown above.

7

stop vs kill — see the difference

Slides 8, 12 · Quiz Q3~3 min

Goal: Prove that stop is graceful and kill is not, using exit codes.

Run from: module1-lab/
Terminal
docker stop web
docker inspect -f 'web      -> exit code {{.State.ExitCode}}' web

docker run -d --name web-kill nginx:1.28-alpine
docker kill web-kill
docker inspect -f 'web-kill -> exit code {{.State.ExitCode}}' web-kill

docker rm web web-kill
Expected output
web      -> exit code 0
web-kill -> exit code 137
What just happened
  • docker stop sends the image's stop signal (nginx uses a graceful SIGQUIT), waits up to 10 seconds, and only then force-kills.
  • docker kill sends SIGKILL immediately. No cleanup at all.
  • 137 = 128 + 9. Signal 9 is SIGKILL. When you see 137, the container was killed.
Checkpoint
Part A done. docker ps -a shows no containers left over from Part A.

Build your first image — RUN vs CMD

Slides 17–20 · Quiz Q4~6 min

Goal: See with your own eyes why RUN alone prints nothing when the container runs.

Run from: module1-lab/first-image/
Make a folder for this image
mkdir first-image
cd first-image

8a. The broken version (a very common mistake)

Creates: Dockerfile.broken
cat > Dockerfile.broken <<'EOF'
FROM ubuntu:24.04
RUN echo "Hello from my first Docker image"
EOF
Terminal
docker build --progress=plain --no-cache -f Dockerfile.broken -t first-image-broken .
docker run --rm first-image-broken
docker inspect -f 'CMD it inherited: {{json .Config.Cmd}}' first-image-broken
Expected output
#5 [2/2] RUN echo "Hello from my first Docker image"
#5 0.176 Hello from my first Docker image     <- printed during the BUILD only
...
                                              <- docker run printed NOTHING
CMD it inherited: ["/bin/bash"]

8b. The fixed version

Creates: Dockerfile
cat > Dockerfile <<'EOF'
FROM ubuntu:24.04
RUN echo "Hello from my first Docker image" > /message.txt
CMD ["cat", "/message.txt"]
EOF
Terminal
docker build -t my_first_image .
docker images my_first_image
docker run --rm my_first_image
Expected output
IMAGE                   ID             DISK USAGE   CONTENT SIZE
my_first_image:latest   7356c028c0df        117MB         29.8MB
Hello from my first Docker image
Go back to module1-lab
cd ..
What just happened
  • RUN runs once, while building. Its output only appears in the build log.
  • The broken image has no CMD of its own, so it inherited Ubuntu's /bin/bash. Bash with no terminal attached exits straight away — so nothing prints.
  • In the fixed image, RUN writes the message into a file inside the image, and CMD prints that file every time a container starts.
  • We pinned ubuntu:24.04. The slide uses ubuntu:latest to keep it short, but pinned versions are what you use in real projects.
Checkpoint
docker run --rm my_first_image prints the message.

Environment variables — same image, different settings

Slide 22~5 min

Goal: Change an app's settings at run time without rebuilding, and learn which setting wins.

Run from: module1-lab/env-demo/
Terminal
mkdir env-demo
cd env-demo
Creates: Dockerfile
cat > Dockerfile <<'EOF'
FROM alpine:3.22
ENV GREETING="Hello (default baked into the image)"
ENV APP_ENV="dev"
CMD ["sh", "-c", "echo \"$GREETING | APP_ENV=$APP_ENV\""]
EOF
Creates: app.env
cat > app.env <<'EOF'
GREETING=Hello from an env file
APP_ENV=staging
EOF
Terminal
docker build -t env-demo .

echo '--- 1. default from ENV ---'
docker run --rm env-demo

echo '--- 2. override with -e ---'
docker run --rm -e GREETING="Hello from -e" env-demo

echo '--- 3. load a file with --env-file ---'
docker run --rm --env-file app.env env-demo

echo '--- 4. both: -e wins ---'
docker run --rm --env-file app.env -e APP_ENV=prod env-demo
Expected output
--- 1. default from ENV ---
Hello (default baked into the image) | APP_ENV=dev
--- 2. override with -e ---
Hello from -e | APP_ENV=dev
--- 3. load a file with --env-file ---
Hello from an env file | APP_ENV=staging
--- 4. both: -e wins ---
Hello from an env file | APP_ENV=prod
Go back to module1-lab
cd ..
What just happened
  • ENV in the Dockerfile is only a default.
  • Priority order: -e > --env-file > ENV.
  • This is how one image runs in dev, staging and production — only the settings change.
Checkpoint
You can explain why run #4 printed APP_ENV=prod.

Keep your data: volumes

Slide 24 · Quiz Q8~4 min

Goal: See data disappear without a volume, then keep it with a named volume.

Run from: module1-lab/

10a. Without a volume, data dies with the container

Terminal
docker run --name temp-writer alpine:3.22 sh -c 'echo "important data" > /data.txt'
docker rm temp-writer
docker run --rm alpine:3.22 cat /data.txt
Expected output
cat: can't open '/data.txt': No such file or directory

10b. Named volume — survives container removal

Terminal
docker volume create app-data

for i in 1 2 3; do
  docker run --rm -v app-data:/data alpine:3.22 sh -c "echo 'run $i wrote this' >> /data/log.txt"
done

docker run --rm -v app-data:/data alpine:3.22 cat /data/log.txt
Expected output
run 1 wrote this
run 2 wrote this
run 3 wrote this
What just happened
  • A container's own filesystem is thrown away with the container. A named volume lives outside it, so the data survives.
  • Kubernetes uses the same idea for databases: a PersistentVolumeClaim (Module 8).
Checkpoint
Part B done. docker volume ls shows app-data, and it still holds three lines.

Create the project files

Slides 26–27~5 min

Goal: Create a small but realistic Node.js API: settings from env vars, a health endpoint, optional Redis, and graceful shutdown.

Run from: module1-lab/demo-api/
Every remaining step runs inside demo-api/
mkdir demo-api
cd demo-api
Creates: app.js
cat > app.js <<'EOF'
const express = require('express');
const os = require('os');
const { createClient } = require('redis');

const PORT = process.env.PORT || 3000;
const GREETING = process.env.GREETING || 'Hello from Module 1!';
const REDIS_URL = process.env.REDIS_URL;

const app = express();
let redis = null;

if (REDIS_URL) {
  redis = createClient({ url: REDIS_URL });
  redis.on('error', (err) => console.error('Redis error:', err.message));
  redis.connect()
    .then(() => console.log('Connected to Redis'))
    .catch((err) => console.error('Redis connect failed:', err.message));
}

app.get('/', async (req, res) => {
  const visits = redis && redis.isReady ? await redis.incr('visits') : null;
  res.json({ message: GREETING, servedBy: os.hostname(), visits });
});

app.get('/health', (req, res) => res.status(200).send('OK'));

const server = app.listen(PORT, () => console.log(`Listening on port ${PORT}`));

process.on('SIGTERM', () => {
  console.log('SIGTERM received - shutting down gracefully');
  server.close(async () => {
    if (redis && redis.isOpen) await redis.close();
    console.log('Shutdown complete');
    process.exit(0);
  });
});
EOF
Creates: package.json
cat > package.json <<'EOF'
{
  "name": "module1-demo-api",
  "version": "1.0.0",
  "private": true,
  "main": "app.js",
  "scripts": {
    "start": "node app.js"
  },
  "dependencies": {
    "express": "^5.2.1",
    "redis": "^6.2.1"
  }
}
EOF
Creates: .dockerignore
cat > .dockerignore <<'EOF'
node_modules
npm-debug.log
.git
.gitignore
.env
*.md
Dockerfile
.dockerignore
EOF
Creates: .env (local settings — kept out of the image)
cat > .env <<'EOF'
GREETING=Hello from my laptop!
EOF
Check
ls -A
Expected output
.dockerignore  .env  app.js  package.json
What just happened
  • app.js reads all settings from environment variables (PORT, GREETING, REDIS_URL) — just like Step 9.
  • /health returns OK. Docker (and later Kubernetes) will call it to check the app is alive.
  • The SIGTERM handler lets the app finish requests and close Redis before it exits. That makes docker stop fast and clean (Step 15).
  • .dockerignore keeps node_modules, .git and .env (secrets!) out of the build (slide 27).
Checkpoint
ls -A shows the four files.

Lock dependencies and write the multi-stage Dockerfile

Slide 26 · Quiz Q5, Q9~6 min

Goal: Create a lock file (no Node.js install needed on your laptop), then write a production Dockerfile.

Run from: module1-lab/demo-api/
Generate package-lock.json using Node inside a container
docker run --rm -v "$(pwd)":/app -w /app node:24-alpine npm install --package-lock-only
ls package-lock.json
Expected output
added ... packages ...
package-lock.json
Note: On Linux the new file may belong to root. Fix it with sudo chown $USER package-lock.json.
Creates: Dockerfile
cat > Dockerfile <<'EOF'
# ---------- Stage 1: install production dependencies ----------
FROM node:24-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

# ---------- Stage 2: small, secure runtime image ----------
FROM node:24-alpine AS runtime
ENV NODE_ENV=production \
    PORT=3000
WORKDIR /app
COPY --from=deps --chown=node:node /app/node_modules ./node_modules
COPY --chown=node:node package.json app.js ./
USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD wget -qO- http://127.0.0.1:3000/health || exit 1
CMD ["node", "app.js"]
EOF
LineWhy it is there
FROM node:24-alpine AS depsStage 1 — the "workshop". Node 24 is the current LTS; Alpine keeps it small.
COPY package.json package-lock.json ./ before the codeDependencies change rarely. Copying them first means Docker reuses the cached npm ci layer when only your code changes (Quiz Q5).
RUN npm ci --omit=devInstalls exact versions from the lock file, production dependencies only.
FROM node:24-alpine AS runtimeStage 2 — starts completely fresh. Nothing from stage 1 comes along unless we copy it.
COPY --from=deps ...Takes only the finished node_modules from the workshop.
--chown=node:node + USER nodeThe app runs as the built-in non-root node user, not root.
HEALTHCHECK ...Docker calls /health every 30s and marks the container healthy or unhealthy.
CMD ["node", "app.js"]Exec form (JSON array) makes node process 1, so it receives SIGTERM from docker stop.
Checkpoint
ls shows Dockerfile and package-lock.json.

15

Graceful shutdown in action

Slides 8, 12 · Quiz Q3~4 min

Goal: See the SIGTERM handler from app.js working — and what happens without one.

Run from: module1-lab/demo-api/
Terminal
time docker stop demo-api
docker logs demo-api
docker inspect -f 'exit code {{.State.ExitCode}}' demo-api
docker rm demo-api
Expected output
demo-api
real    0m0.202s

Listening on port 3000
SIGTERM received - shutting down gracefully
Shutdown complete
exit code 0
Compare: an app with no SIGTERM handler
docker run -d --name no-handler node:24-alpine node -e 'setInterval(() => {}, 1000)'
time docker stop no-handler
docker inspect -f 'exit code {{.State.ExitCode}}' no-handler
docker rm no-handler
Expected output
no-handler
real    0m10.159s
exit code 137
What just happened
  • Our app caught SIGTERM, finished up, and exited with code 0 in about 0.2 seconds.
  • The app with no handler ignored SIGTERM. Docker waited the full 10 seconds, then sent SIGKILL → exit code 137.
  • Kubernetes stops containers the same way. Apps that handle SIGTERM deploy and scale much more smoothly.
Checkpoint
Part C done. Your image is built, pushed, healthy, non-root and shuts down cleanly.

What just happened
  • 2>/dev/null hides "No such container" errors for things you already removed.
  • -v in docker rm -fv also deletes anonymous volumes, so nothing is left behind.
  • docker logout removes your Docker Hub login from this machine. The images stay on Docker Hub — Module 2 pulls them from there; delete the repository in Docker Hub's settings when you no longer need it.
  • Prune commands never touch anything that is running or in use.

Troubleshooting

Bind for 0.0.0.0:8080 failed: port is already allocated
Another container (or app) uses that port. Find it with docker ps and stop it, or change the host side: -p 8090:80.
Conflict. The container name "/web" is already in use
An old container with that name still exists (maybe stopped). Remove it: docker rm -f web.
permission denied while trying to connect to the Docker daemon socket
Linux only: add yourself to the docker group — sudo usermod -aG docker $USER — then log out and back in.
Cannot connect to the Docker daemon
Docker Desktop is not running (Mac/Windows), or start the service: sudo systemctl start docker (Linux).
toomanyrequests: You have reached your pull rate limit
Docker Hub limits anonymous pulls. Run docker login with a free Docker Hub account.
curl: command not found or odd output on Windows
Use curl.exe in PowerShell, or open the URL in your browser.
Step 12: npm ci fails with "package-lock.json not found"
You skipped the lock-file command at the top of Step 12. Run it, then build again.
Step 13: status stays (health: starting)
The first check happens after up to 10 seconds. Wait, then run docker ps again. If it becomes unhealthy, check docker logs demo-api.
Step 14: denied: requested access to the resource is denied
You are not logged in, or DOCKERHUB_USER is not your own account. Run docker login -u <your user> and tag with your user name.
