Before you start

  • Finish Module 2 first. This lab uses the same 3-node kind cluster (kind-lab).
  • Terminal: bash or zsh — macOS Terminal, Linux, or WSL2 on Windows.
  • Go in order, and check every Checkpoint. Pod IPs, ports, times and random suffixes will differ from yours — that's normal.
  • Something failed? See Troubleshooting at the bottom.
Trainers: pre-load the lab images into the kind cluster before class

  docker pull --platform "$PLATFORM" "$img"
  docker save --platform "$PLATFORM" -o image.tar "$img"
  kind load image-archive image.tar --name lab
done

Generate YAML, then apply it

Slides 16–18, 28~5 min

Goal: Let kubectl write a draft manifest, compare it with the clean pod.yaml, and create the Pod declaratively.

Run from: module3-lab/
Draft a manifest — nothing is created
kubectl run nginx-pod --image=nginx:1.28-alpine --port=80 -l app=nginx \
  --dry-run=client -o yaml
Expected output
apiVersion: v1
kind: Pod
metadata:
  labels:
    app: nginx
  name: nginx-pod
spec:
  containers:
  - image: nginx:1.28-alpine
    name: nginx-pod
    ports:
    - containerPort: 80
    resources: {}
  dnsPolicy: ClusterFirst
  restartPolicy: Always
status: {}
Creates: pod.yaml (the clean version from slide 17)
cat > pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:1.28-alpine
      ports:
        - containerPort: 80
EOF
Terminal
kubectl apply -f pod.yaml
kubectl wait --for=condition=Ready pod/nginx-pod --timeout=60s
kubectl get pod nginx-pod --show-labels
Expected output
pod/nginx-pod created
pod/nginx-pod condition met
NAME        READY   STATUS    RESTARTS   AGE   LABELS
nginx-pod   1/1     Running   0          2s    app=nginx
What just happened
  • Every manifest has the same four top-level keys: apiVersion → kind → metadata → spec.
  • --dry-run=client -o yaml gives you a correct starting point. Delete the empty fields (resources: {}, status: {}) and keep the rest.
  • The label app: nginx matters — the Service in Step 8 finds the Pod through it.
  • Imperative: "run this". Declarative: "make the cluster match this file". From now on we use files.
Checkpoint
The Pod is Running with the label app=nginx.
4

Talk to a Pod by its IP

Slides 5, 13~3 min

Goal: Reach nginx from another Pod using its Pod IP, and see why that IP isn't something to rely on.

Run from: module3-lab/
Terminal
POD_IP=$(kubectl get pod nginx-pod -o jsonpath='{.status.podIP}')
echo "nginx-pod IP: $POD_IP"
kubectl exec client -- wget -qO- http://$POD_IP | grep title
Expected output
nginx-pod IP: 10.244.1.2
<title>Welcome to nginx!</title>
What just happened
  • Every Pod gets its own IP on the cluster network. Any Pod can reach any other Pod directly.
  • That IP only exists inside the cluster. From your laptop, curl 10.244.x.x would just time out.
  • And it changes whenever the Pod is recreated — Step 11 proves it. That's why we need Services.
Checkpoint
You saw Welcome to nginx! through the Pod IP.

Watch the lifecycle: Pending → Running → Succeeded

Slides 6–7, 29 · Quiz Q8~5 min

Goal: Run a Pod that does one job and exits, and watch it move through every phase.

Run from: module3-lab/
Watch for 12 seconds
kubectl run short-job --image=busybox:1.37 --restart=Never -- sh -c 'echo working; sleep 5; echo done'
kubectl get pod short-job -w --request-timeout=12s
Expected output
pod/short-job created
NAME        READY   STATUS              RESTARTS   AGE
short-job   0/1     ContainerCreating   0          0s
short-job   1/1     Running             0          1s
short-job   0/1     Completed           0          7s
Check the phase and the output
kubectl get pod short-job -o jsonpath='{.status.phase}{"\n"}'
kubectl logs short-job
Expected output
Succeeded
working
done
Compare: a container that exits with an error
kubectl run fail-once --image=busybox:1.37 --restart=Never -- sh -c 'echo oops; exit 3'
sleep 5
kubectl get pod fail-once -o jsonpath='phase={.status.phase} exitCode={.status.containerStatuses[0].state.terminated.exitCode}{"\n"}'
Expected output
pod/fail-once created
phase=Failed exitCode=3
You sawPod phaseContainer state
ContainerCreatingPendingWaiting
RunningRunningRunning
Completed (exit 0)SucceededTerminated
Error (exit 3)FailedTerminated
What just happened
  • --restart=Never means: when the container stops, don't start it again. That's what lets the Pod finish.
  • The STATUS column shows a friendly summary. The real phase lives in .status.phase.
  • -w watches for changes. --request-timeout stops the watch for you (or press Ctrl + C).
Checkpoint
short-job is Succeeded and fail-once is Failed.
6

ImagePullBackOff — a bad image tag

Slides 8, 30 · Quiz Q5~4 min

Goal: Create a Pod with an image tag that doesn't exist, and find the reason in the events.

Run from: module3-lab/
Terminal
kubectl run bad-image --image=nginx:9.99-doesnotexist
sleep 20
kubectl get pod bad-image
kubectl describe pod bad-image | grep -E 'Warning' | head -3
Expected output
pod/bad-image created
NAME        READY   STATUS             RESTARTS   AGE
bad-image   0/1     ImagePullBackOff   0          20s
  Warning  Failed   15s (x2 over 20s)  kubelet  spec.containers{bad-image}: Failed to pull image "nginx:9.99-doesnotexist": ... not found
  Warning  Failed   15s (x2 over 20s)  kubelet  spec.containers{bad-image}: Error: ErrImagePull
  Warning  Failed   3s (x2 over 19s)   kubelet  spec.containers{bad-image}: Error: ImagePullBackOff
What just happened
  • ErrImagePull is the failure. ImagePullBackOff means the kubelet is now waiting longer and longer between retries.
  • The event message tells you why: not found (bad name or tag), unauthorized (a private registry needs credentials), or a network error.
  • The fix is always in the Pod spec — correct the image. Deleting and re-creating the same Pod won't help.
Checkpoint
You found the words not found in the events.

CrashLoopBackOff — read the real error

Slides 8, 30 · Quiz Q4~5 min

Goal: Run an app that crashes on start-up, and use logs and describe to find the root cause.

Run from: module3-lab/
Terminal
kubectl run crasher --image=busybox:1.37 -- \
  sh -c 'echo "starting app..."; echo "ERROR: DATABASE_URL is not set"; exit 1'
sleep 45
kubectl get pod crasher
Expected output
pod/crasher created
NAME      READY   STATUS             RESTARTS      AGE
crasher   0/1     CrashLoopBackOff   3 (28s ago)   45s
Find the cause
kubectl logs crasher
kubectl describe pod crasher | grep -E 'Last State|Exit Code|Restart Count|BackOff'
Expected output
starting app...
ERROR: DATABASE_URL is not set
      Exit Code:    1
    Last State:     Terminated
      Exit Code:    1
    Restart Count:  3
  Warning  BackOff    11s (x3 over 43s)  kubelet  ... Back-off restarting failed container crasher ...
What just happened
  • kubectl run uses restartPolicy: Always, so the kubelet restarts the crashing container — waiting 10 s, 20 s, 40 s… up to 5 minutes.
  • STATUS flips between Error and CrashLoopBackOff. Both mean the same thing: it keeps crashing.
  • CrashLoopBackOff is only the symptom. The cause is in the logs: a missing setting. The fix is in the app's configuration (Module 6).
  • Use kubectl logs --previous when a container crashed and has already restarted and is running again — it shows the crashed run's output.
Checkpoint
You found DATABASE_URL is not set in the logs.

Create a Service from YAML

Slides 19–24~5 min

Goal: Put a stable name and IP in front of nginx-pod with a ClusterIP Service.

Run from: module3-lab/
Creates: service.yaml
cat > service.yaml <<'EOF'
apiVersion: v1
kind: Service
metadata:
  name: nginx-svc
spec:
  type: ClusterIP
  selector:
    app: nginx
  ports:
    - protocol: TCP
      port: 80
      targetPort: 80
EOF
Terminal
kubectl apply -f service.yaml
kubectl get service nginx-svc
kubectl describe service nginx-svc | grep -E 'Selector|Type:|^IP:|Port|Endpoints'
kubectl get endpointslices -l kubernetes.io/service-name=nginx-svc
Expected output
service/nginx-svc created
NAME        TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
nginx-svc   ClusterIP   10.96.189.200   <none>        80/TCP    0s
Selector:                 app=nginx
Type:                     ClusterIP
IP:                       10.96.189.200
Port:                     <unset>  80/TCP
TargetPort:               80/TCP
Endpoints:                10.244.1.2:80
NAME              ADDRESSTYPE   PORTS   ENDPOINTS    AGE
nginx-svc-n2v26   IPv4          80      10.244.1.2   1s
What just happened
  • The Service got a stable ClusterIP (10.96.189.200). It never changes while the Service exists.
  • Selector app=nginx found our Pod — its IP shows up as the Endpoint.
  • port: 80 is where clients connect. targetPort: 80 is where the Pod listens. They must match what the app really uses (Quiz Q7).
  • Kubernetes tracks endpoints in EndpointSlice objects. kube-proxy on every node reads them to route traffic (Module 2).
Checkpoint
Endpoints shows nginx-pod's IP.

Service discovery with DNS

Slides 25, 31 · Quiz Q9~5 min

Goal: Reach nginx by the Service's name, look up its full DNS name, and prove Pods have no names of their own.

Run from: module3-lab/
Terminal
kubectl exec client -- wget -qO- http://nginx-svc | grep title
kubectl exec client -- nslookup nginx-svc.default.svc.cluster.local
kubectl exec client -- cat /etc/resolv.conf
Expected output
<title>Welcome to nginx!</title>
Server:		10.96.0.10
Address:	10.96.0.10:53

Name:	nginx-svc.default.svc.cluster.local
Address: 10.96.189.200

search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5
Pods do NOT get a DNS name
kubectl exec client -- wget -qO- -T 3 http://nginx-pod
Expected output
wget: bad address 'nginx-pod'
command terminated with exit code 1
What just happened
  • The full name is <service>.<namespace>.svc.cluster.local. CoreDNS answers at 10.96.0.10.
  • The search line lets you use short names: nginx-svc works inside the same namespace. From another namespace, use nginx-svc.default.
  • nginx-pod doesn't resolve — only Services get names. Always talk to a Service, never to a Pod directly.
Checkpoint
nginx-svc works and nginx-pod gives bad address.

Labels decide which Pods a Service uses

Slides 22, 32, 37 · Quiz Q3~5 min

Goal: Break the selector match on purpose, watch the endpoint disappear, then fix it.

Run from: module3-lab/
Change the Pod's label
kubectl label pod nginx-pod app=web --overwrite
sleep 2
kubectl get endpointslices -l kubernetes.io/service-name=nginx-svc
kubectl exec client -- wget -qO- -T 3 http://nginx-svc
Expected output
pod/nginx-pod labeled
NAME              ADDRESSTYPE   PORTS     ENDPOINTS   AGE
nginx-svc-n2v26   IPv4          <unset>   <unset>     2m
wget: can't connect to remote host (10.96.189.200): Connection refused
command terminated with exit code 1
Put the label back
kubectl label pod nginx-pod app=nginx --overwrite
sleep 2
kubectl get endpointslices -l kubernetes.io/service-name=nginx-svc
kubectl exec client -- wget -qO- http://nginx-svc | grep title
Expected output
pod/nginx-pod labeled
NAME              ADDRESSTYPE   PORTS   ENDPOINTS    AGE
nginx-svc-n2v26   IPv4          80      10.244.1.2   2m
<title>Welcome to nginx!</title>
What just happened
  • A Service doesn't point at Pods by name. It points at whatever Pods have matching labels, right now.
  • No match = no endpoints = connection refused, even though the Pod is perfectly healthy.
  • This is the #1 Service bug in real life: a typo in a label or selector. Check endpoints first.
Checkpoint
Endpoints came back and Welcome to nginx! works again.

The Service survives Pod replacement

Slides 19, 33 · Quiz Q2~4 min

Goal: Replace the Pod, see its IP change, and prove the Service name still works.

Run from: module3-lab/
Terminal
kubectl get pod nginx-pod -o jsonpath='old IP: {.status.podIP}{"\n"}'
kubectl delete pod nginx-pod
kubectl apply -f pod.yaml
kubectl wait --for=condition=Ready pod/nginx-pod --timeout=60s
kubectl get pod nginx-pod -o jsonpath='new IP: {.status.podIP}{"\n"}'
kubectl get endpointslices -l kubernetes.io/service-name=nginx-svc
kubectl exec client -- wget -qO- http://nginx-svc | grep title
Expected output
old IP: 10.244.1.2
pod "nginx-pod" deleted from default namespace
pod/nginx-pod created
pod/nginx-pod condition met
new IP: 10.244.1.3
NAME              ADDRESSTYPE   PORTS   ENDPOINTS    AGE
nginx-svc-n2v26   IPv4          80      10.244.1.3   2m
<title>Welcome to nginx!</title>
What just happened
  • A new Pod always gets a new IP. Anything that saved the old IP is now broken.
  • The Service's selector found the new Pod automatically, and its endpoint moved to the new IP.
  • Clients using nginx-svc never noticed. That's the whole point of a Service.
Checkpoint
The IP changed, but nginx-svc still answers.

Reach it from outside: NodePort and port-forward

Slides 21, 23~6 min

Goal: Expose nginx on a port on every node, then reach it from your laptop.

Run from: module3-lab/
Terminal
kubectl expose pod nginx-pod --type=NodePort --port=80 --name=nginx-nodeport
kubectl get service nginx-nodeport
NODE_PORT=$(kubectl get service nginx-nodeport -o jsonpath='{.spec.ports[0].nodePort}')
echo "NodePort: $NODE_PORT"
Expected output
service/nginx-nodeport exposed
NAME             TYPE       CLUSTER-IP    EXTERNAL-IP   PORT(S)        AGE
nginx-nodeport   NodePort   10.96.12.57   <none>        80:32353/TCP   0s
NodePort: 32353
Call the NodePort on every node (from inside kind's Docker network)
sleep 3   # give kube-proxy a moment to program every node
for node in lab-control-plane lab-worker lab-worker2; do
  docker exec lab-control-plane curl -s -o /dev/null -w "$node:$NODE_PORT -> %{http_code}\n" http://$node:$NODE_PORT
done
Expected output
lab-control-plane:32353 -> 200
lab-worker:32353 -> 200
lab-worker2:32353 -> 200
From your laptop: port-forward
kubectl port-forward service/nginx-svc 8080:80 >/dev/null &
PF_PID=$!
sleep 2
curl -s http://localhost:8080 | grep title
kill $PF_PID
Expected output
<title>Welcome to nginx!</title>
What just happened
  • A NodePort opens the same port on every node (30000–32767) — even nodes that don't run the Pod. kube-proxy forwards the traffic.
  • kind nodes are containers, so we tested from inside kind's network. On a real cluster you'd use http://<node-ip>:<nodePort>.
  • port-forward is the everyday way to reach a Service from your laptop while developing.
  • We used --name=nginx-nodeport so the Service isn't called nginx-pod — a Service and a Pod with the same name is confusing.
Careful: Don't mix kubectl expose and kubectl apply on the same Service. apply will warn about a missing last-applied-configuration and quietly change the Service. Pick one way per object — files are best.
Checkpoint
All three nodes returned 200, and port-forward showed the nginx page.

Two containers, one Pod

Slides 3–4, 34 · Quiz Q1~6 min

Goal: Run nginx and a helper container in one Pod, and prove they share localhost and a volume.

Run from: module3-lab/
Creates: two-containers.yaml
cat > two-containers.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: two-containers
  labels:
    app: shared-demo
spec:
  volumes:
    - name: shared-html
      emptyDir: {}
  containers:
    - name: web
      image: nginx:1.28-alpine
      ports:
        - containerPort: 80
      volumeMounts:
        - name: shared-html
          mountPath: /usr/share/nginx/html
    - name: writer
      image: busybox:1.37
      command: ["sh", "-c"]
      args:
        - while true; do
            echo "<h1>Written by the writer container at $(date +%T)</h1>" > /html/index.html;
            sleep 5;
          done
      volumeMounts:
        - name: shared-html
          mountPath: /html
EOF
Terminal
kubectl apply -f two-containers.yaml
kubectl wait --for=condition=Ready pod/two-containers --timeout=60s
kubectl get pod two-containers
Expected output
pod/two-containers created
pod/two-containers condition met
NAME             READY   STATUS    RESTARTS   AGE
two-containers   2/2     Running   0          2s
The writer calls nginx over localhost
kubectl exec two-containers -c writer -- wget -qO- http://localhost:80
kubectl logs two-containers -c web --tail=1
Expected output
<h1>Written by the writer container at 17:44:41</h1>
127.0.0.1 - - [28/Sep/2026:17:44:41 +0000] "GET / HTTP/1.1" 200 53 "-" "Wget" "-"
What just happened
  • READY 2/2: one Pod, two containers, scheduled together on the same node.
  • Shared network: writer reached nginx at localhost:80, and nginx logged the visitor as 127.0.0.1.
  • Shared volume: nginx served the page that writer wrote into the emptyDir volume.
  • Use -c <name> to pick a container for logs and exec.
Checkpoint
The page says Written by the writer container.
14

2026 features: native sidecar and in-place resize

Slides 35–36~6 min

Goal: Run a native sidecar that ships nginx's logs, then change the Pod's CPU without restarting it.

Run from: module3-lab/
Creates: sidecar-resize.yaml
cat > sidecar-resize.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: modern-pod
spec:
  initContainers:
    - name: log-shipper
      image: busybox:1.37
      restartPolicy: Always
      command: ["sh", "-c", "tail -F /logs/access.log"]
      volumeMounts:
        - name: logs
          mountPath: /logs
  containers:
    - name: web
      image: nginx:1.28-alpine
      resources:
        requests:
          cpu: 100m
          memory: 64Mi
        limits:
          cpu: 200m
          memory: 128Mi
      resizePolicy:
        - resourceName: cpu
          restartPolicy: NotRequired
        - resourceName: memory
          restartPolicy: RestartContainer
      volumeMounts:
        - name: logs
          mountPath: /var/log/nginx
  volumes:
    - name: logs
      emptyDir: {}
EOF

What just happened
  • Native sidecar (stable since v1.33): an initContainer with restartPolicy: Always. It starts first, keeps running beside the app, and stops after it.
  • The sidecar reads nginx's log file from a shared volume — a common pattern for log shipping.
  • In-place resize (stable since v1.35): change CPU or memory with --subresource resize. With restartPolicy: NotRequired for CPU, the container keeps running — restarts=0.
  • Memory in this file uses RestartContainer, because many apps only read their memory size at start-up.

Part E — User namespacesStep 15 · root in the Pod, not on the node · ~6 min
15

User namespaces: root in the Pod, nobody on the node

Slide 37~6 min

Goal: Run the same command as root in two Pods — one with its own user namespace — and see which UID each really has on the node.

Run from: module3-lab/
Creates: userns-pod.yaml
cat > userns-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: userns-pod
spec:
  hostUsers: false          # give this Pod its own user namespace
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3700"]
EOF
Inside the Pods
kubectl apply -f userns-pod.yaml
kubectl run normal-pod --image=busybox:1.37 -- sleep 3701
kubectl wait --for=condition=Ready pod/userns-pod pod/normal-pod --timeout=60s
kubectl exec userns-pod -- id
kubectl exec userns-pod -- cat /proc/self/uid_map
kubectl exec normal-pod -- cat /proc/self/uid_map
Expected output
pod/userns-pod created
pod/normal-pod created
pod/userns-pod condition met
pod/normal-pod condition met
uid=0(root) gid=0(root) groups=0(root),10(wheel)
         0 4153409536      65536
         0          0 4294967295
On the node (kind nodes are containers, so we can look)
for p in userns-pod:3700 normal-pod:3701; do
  pod=${p%:*}; secs=${p#*:}
  node=$(kubectl get pod $pod -o jsonpath='{.spec.nodeName}')
  echo "$pod on $node runs as host UID $(docker exec $node sh -c "stat -c %u /proc/\$(pgrep -f '^sleep $secs')")"
done
Expected output
userns-pod on lab-worker runs as host UID 4153409536
normal-pod on lab-worker runs as host UID 0
What just happened
  • Both containers think they're root (uid 0). The uid_map line shows the truth: in userns-pod, uid 0 inside maps to a high, unprivileged UID on the node; in normal-pod, uid 0 is uid 0 on the node.
  • If an attacker breaks out of userns-pod's container, they land on the node as a nobody — not as root. That's why hostUsers: false is one of the strongest single protections you can add.
  • User namespaces are stable in Kubernetes v1.37. They need a recent Linux kernel and container runtime — kind on a current Docker host has both.
  • Apps that really need host-level powers (loading kernel modules, host networking tools) can't use it. For normal apps it's usually free.
Checkpoint
userns-pod maps to a large host UID (the exact number changes every time), normal-pod to 0. The node names may differ too.

Troubleshooting

error: the server doesn't have a resource type or connection refused
kubectl can't reach the cluster. Check kind get clusters and kubectl config current-context (Step 1).
Error from server (AlreadyExists): pods "client" already exists
It's still there from a previous run. Use it, or remove it: kubectl delete pod client --now.
wget: bad address 'nginx-svc'
The Service doesn't exist or is in another namespace. Check kubectl get svc. From another namespace, use nginx-svc.default.
Connection refused to a Service
No endpoints. Compare kubectl get pods --show-labels with the Service's selector (Step 10).
A Pod stays Pending
Run kubectl describe pod <name> and read Events. Usually no node fits, or nodes aren't Ready.
kubectl logs says a container name must be specified
The Pod has more than one container. Add -c <container> (Step 13).
error: unknown flag: --subresource
Your kubectl is too old for in-place resize. Use kubectl v1.32 or newer.
port-forward says address already in use
Something already uses port 8080. Pick another local port: kubectl port-forward service/nginx-svc 8081:80.
kind load fails with ctr: content digest sha256:… not found
Docker 29 keeps images in its containerd image store: it downloads only your platform, but docker save still lists all of them, and kind's import looks for every one. Save just your platform and load the archive — that's what the pre-load commands at the top of this page do: docker save --platform "$(docker version --format '{{.Server.Os}}/{{.Server.Arch}}')" -o image.tar IMAGE then kind load image-archive image.tar --name lab. Images you built yourself (like module1-demo-api) load fine with kind load docker-image.
ERROR: unknown containerd config version: 4 from kind
Your kind binary is older than the node image. Install kind v0.33 or newer (Module 2, Step 1) and run kind version to check.
