Before you start

  • Finish Modules 2–8 first. This lab uses the 3-node kind cluster (kind-lab) and its admin context.
  • Terminal: bash or zsh — macOS Terminal, Linux, or WSL2 on Windows — with openssl (preinstalled on macOS and most Linux).
  • Go in order, and check every Checkpoint. Pod counts, ages, IDs and dates will differ from yours — that's normal.
  • Something failed? See Troubleshooting at the bottom.

Who am I? The admin you've been all along

Slides 3–5~4 min

Goal: Check the cluster, create the lab folder, and find out which identity kubectl has been using.

Run from: module9-lab/
Create the lab folder — every step runs from here
# Create the lab working folder
mkdir module9-lab
# Move into the lab folder
cd module9-lab
Who is kubectl talking as?
# List the cluster nodes and confirm all are Ready
kubectl get nodes
# List kubectl contexts to see which cluster and user you are using
kubectl config get-contexts
# Show who the API server thinks you are
kubectl auth whoami
# Check that your current admin user can do everything
kubectl auth can-i '*' '*'
Expected output
NAME                STATUS   ROLES           AGE   VERSION
lab-control-plane   Ready    control-plane   11h   v1.37.0
lab-worker          Ready    <none>          11h   v1.37.0
lab-worker2         Ready    <none>          11h   v1.37.0
CURRENT   NAME       CLUSTER    AUTHINFO   NAMESPACE
*         kind-lab   kind-lab   kind-lab   default
ATTRIBUTE                                           VALUE
Username                                            kubernetes-admin
Groups                                              [kubeadm:cluster-admins system:authenticated]
Extra: authentication.kubernetes.io/credential-id   [X509SHA256=4bc2b81f…]
yes
What just happened
  • Every request to the API server goes through three gates: authentication (who are you?), authorization (may you do this?) and admission (is this object allowed?). RBAC is the authorization gate.
  • Since Module 2 you've been kubernetes-admin, in the group kubeadm:cluster-admins. can-i '*' '*' → yes: you may do everything, everywhere.
  • That's fine for learning, and dangerous for anything else. A leaked admin credential is a leaked cluster. Today we build identities that can do only their job.
Checkpoint
You are kubernetes-admin, and can-i '*' '*' says yes.
2

A real user: jai, signed by the cluster

Slides 12, 26~8 min

Goal: Create a user with a client certificate that Kubernetes itself signs, add it to kubeconfig, and see authentication work while authorization says no.

Run from: module9-lab/
jai's private key and certificate request (CN = user, O = group)
# Generate a private key for the new user jai
openssl genrsa -out jai.key 2048
# Create a certificate signing request with CN=jai and group developers
openssl req -new -key jai.key -out jai.csr -subj "/CN=jai/O=developers"
Ask the cluster to sign it — then approve as admin
# Create the YAML for a Kubernetes CertificateSigningRequest holding that request
cat > jai-csr.yaml <<EOF
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: jai
spec:
  request: $(base64 < jai.csr | tr -d '\n')
  signerName: kubernetes.io/kube-apiserver-client   # a client certificate for the API server
  expirationSeconds: 86400                          # valid for one day
  usages:
    - client auth
EOF
# Submit the signing request to the cluster
kubectl apply -f jai-csr.yaml
# Show the request is Pending approval
kubectl get csr jai
# Approve the request as cluster admin
kubectl certificate approve jai
# Extract the signed certificate into jai.crt
kubectl get csr jai -o jsonpath='{.status.certificate}' | base64 -d > jai.crt
# Inspect the certificate's subject, issuer and expiry
openssl x509 -in jai.crt -noout -subject -issuer -enddate
Expected output
certificatesigningrequest.certificates.k8s.io/jai created
NAME   AGE   SIGNERNAME                            REQUESTOR          REQUESTEDDURATION   CONDITION
jai    0s    kubernetes.io/kube-apiserver-client   kubernetes-admin   24h                 Pending
certificatesigningrequest.certificates.k8s.io/jai approved
subject=O = developers, CN = jai
issuer=CN = kubernetes
notAfter=Sep 30 16:26:39 2026 GMT
Use it
# Add jai's key and certificate to your kubeconfig as a user
kubectl config set-credentials jai --client-certificate=jai.crt --client-key=jai.key --embed-certs=true
# Create a kubectl context that uses jai on the kind-lab cluster
kubectl config set-context jai --cluster=kind-lab --user=jai --namespace=default
# Confirm the API server now identifies you as jai
kubectl --context jai auth whoami
# Try to list Pods as jai — Forbidden, since jai has no permissions yet
kubectl --context jai get pods
Expected output
User "jai" set.
Context "jai" created.
ATTRIBUTE                                           VALUE
Username                                            jai
Groups                                              [developers system:authenticated]
Extra: authentication.kubernetes.io/credential-id   [X509SHA256=a3926d53…]
Error from server (Forbidden): pods is forbidden: User "jai" cannot list resource "pods" in API group "" in the namespace "default"
What just happened
  • Kubernetes has no user objects. A user is whatever a trusted credential says: here the certificate's CN is the username and each O is a group.
  • The CertificateSigningRequest API lets the cluster sign the certificate. Nobody had to copy the cluster's CA private key — the old way on slide 12, which is how whole clusters get compromised.
  • Authentication worked: the API knows it's jai, in group developers. Authorization said Forbidden: RBAC denies everything until something is granted. That's the safe default.
  • --context jai switches identity for one command. We keep using the admin context for setup.
  • On EKS, GKE and AKS, people usually log in through the cloud's identity system (OIDC/IAM) instead of certificates. The RBAC part you learn next is exactly the same.
Checkpoint
auth whoami as jai shows group developers, and get pods is Forbidden.

Role + RoleBinding: read Pods in one namespace

Slides 6–10, 27~6 min

Goal: Give jai read access to Pods in default — and nothing else.

Run from: module9-lab/
Creates: role.yaml
# Create the YAML for a Role that only allows reading Pods in default
cat > role.yaml <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
  - apiGroups: [""]            # "" = the core API group, where Pods live
    resources: ["pods"]
    verbs: ["get", "list"]
EOF
Creates: rolebinding.yaml
# Create the YAML for a RoleBinding that gives jai that Role
cat > rolebinding.yaml <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: default
subjects:
  - kind: User
    name: jai
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
EOF
The Role alone, then the binding
# Start a test Pod for jai to look at
kubectl run web --image=nginx:1.28-alpine
# Wait until the test Pod is Ready
kubectl wait --for=condition=Ready pod/web --timeout=60s
# Create the Role (still not bound to anyone)
kubectl apply -f role.yaml
# Try again as jai — still Forbidden, a Role alone grants nothing
kubectl --context jai get pods
# Bind the Role to jai
kubectl apply -f rolebinding.yaml
# List Pods as jai — now it works
kubectl --context jai get pods
Expected output
pod/web created
pod/web condition met
role.rbac.authorization.k8s.io/pod-reader created
Error from server (Forbidden): pods is forbidden: User "jai" cannot list resource "pods" in API group "" in the namespace "default"
rolebinding.rbac.authorization.k8s.io/pod-reader-binding created
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          2s
What jai still can't do
# Try to delete a Pod as jai — Forbidden, the Role only allows reading
kubectl --context jai delete pod web
# Try to list Pods in kube-system as jai — Forbidden, the Role is namespaced
kubectl --context jai get pods -n kube-system
# Try to read Pod logs as jai — Forbidden, logs are a separate subresource
kubectl --context jai logs web
Expected output
Error from server (Forbidden): pods "web" is forbidden: User "jai" cannot delete resource "pods" in API group "" in the namespace "default"
Error from server (Forbidden): pods is forbidden: User "jai" cannot list resource "pods" in API group "" in the namespace "kube-system"
Error from server (Forbidden): pods "web" is forbidden: User "jai" cannot get resource "pods/log" in API group "" in the namespace "default"
What just happened
  • A Role is a list of rules: which verbs on which resources in which apiGroup. "" is the core group, where Pods live.
  • The Role alone changed nothing. A RoleBinding attaches it to a subject — here the user jai. Both live in default, so that's the only place it counts.
  • RBAC only adds permissions. There are no "deny" rules: whatever isn't granted is refused.
  • Logs are a separate sub-resource, pods/log. "Read Pods" doesn't include "read their logs" — you'd add pods/log to the rule.
Checkpoint
jai can list Pods in default, but can't delete them, list kube-system, or read logs.

Ask before you act: kubectl auth can-i

Slides 11, 27, 33~5 min

Goal: Check permissions without trying the real action — and learn the two ways can-i can fool you.

Run from: module9-lab/
As admin, impersonate jai
# Check several actions at once with can-i, impersonating jai
for q in "list pods" "delete pods" "list pods -n kube-system" "list secrets"; do echo "$q: $(kubectl auth can-i $q --as=jai)"; done
# List everything jai may do (first lines)
kubectl auth can-i --list --as=jai | head -5
Expected output
list pods: yes
delete pods: no
list pods -n kube-system: no
list secrets: no
Resources                                       Non-Resource URLs   Resource Names   Verbs
selfsubjectreviews.authentication.k8s.io        []                  []               [create]
selfsubjectaccessreviews.authorization.k8s.io   []                  []               [create]
selfsubjectrulesreviews.authorization.k8s.io    []                  []               [create]
pods                                            []                  []               [get list]
Gotcha: the slash means a name, not a sub-resource
# Check Pod logs by resource name — misleadingly says yes
kubectl auth can-i get pods/log --as=jai
# Check Pod logs with --subresource=log — the accurate answer is no
kubectl auth can-i get pods --subresource=log --as=jai
Expected output
yes
no
What just happened
  • --as=jai is impersonation: the admin asks "what would happen if jai did this?". The answer comes from the same authorizer the real request would hit.
  • --list shows everything a subject may do in the namespace — the fastest way to review an account.
  • pods/log after can-i get means "the Pod named log". jai may get any Pod, so: yes. The real question needs --subresource=log — and the answer is no, just like the real kubectl logs in Step 3.
  • When in doubt, run the real command with --context. can-i answers exactly the question you typed, not the one you meant.
Checkpoint
list pods yes, everything else no, and --subresource=log says no.

ClusterRole + ClusterRoleBinding: every namespace

Slides 13–17, 28~5 min

Goal: Widen jai's Pod reading to the whole cluster, and prove the difference with a namespace that was denied.

Run from: module9-lab/
Creates: clusterrole.yaml
# Create the YAML for a ClusterRole that can read Pods everywhere
cat > clusterrole.yaml <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: cluster-pod-reader          # no namespace: ClusterRoles are cluster-scoped
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
EOF
Creates: clusterrolebinding.yaml
# Create the YAML for a ClusterRoleBinding that grants it to jai
cat > clusterrolebinding.yaml <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: cluster-pod-reader-binding
subjects:
  - kind: User
    name: jai
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: cluster-pod-reader
  apiGroup: rbac.authorization.k8s.io
EOF
Terminal
# Check jai's access to kube-system Pods before the binding
echo "before: $(kubectl auth can-i list pods -n kube-system --as=jai)"
# Create the ClusterRole and ClusterRoleBinding
kubectl apply -f clusterrole.yaml -f clusterrolebinding.yaml
# Check the same access after the binding — now allowed
echo "after:  $(kubectl auth can-i list pods -n kube-system --as=jai)"
# List Pods across all namespaces as jai and count them
kubectl --context jai get pods -A --no-headers | wc -l
# Check whether jai can list nodes (cluster-scoped resource)
kubectl auth can-i list nodes --as=jai
Expected output
before: no
clusterrole.rbac.authorization.k8s.io/cluster-pod-reader created
clusterrolebinding.rbac.authorization.k8s.io/cluster-pod-reader-binding created
after:  yes
15
Warning: resource 'nodes' is not namespace scoped

no
What just happened
  • A ClusterRole has no namespace. Bound with a ClusterRoleBinding, its rules apply in every namespace — now jai can list all 15 Pods, including kube-system.
  • The old slide checked list pods in default after the change — but jai could already do that. Always test a place that was denied before, or you've proven nothing.
  • Nodes are still no: the ClusterRole only mentions Pods. Cluster-wide doesn't mean everything.
  • Cluster-wide bindings are powerful. For "the same rules in a few namespaces", use a ClusterRole with RoleBindings instead (Step 7).
Checkpoint
kube-system went from no to yes, and nodes are still no.

Cluster-scoped things need a ClusterRole

Slides 13, 18, 28~5 min

Goal: Try to grant access to Nodes with a namespaced Role, watch can-i mislead you, then do it right.

Run from: module9-lab/
The wrong way: a Role
# Create a namespaced Role for nodes (the wrong tool for the job)
kubectl create role node-reader --verb=get,list --resource=nodes -n default
# Bind that Role to jai
kubectl create rolebinding node-reader --role=node-reader --user=jai -n default
# Re-check node access — can-i misleadingly says yes (it checks the default namespace)
kubectl auth can-i list nodes --as=jai
# Try to list nodes as jai — Forbidden
kubectl --context jai get nodes
Expected output
Warning: resource 'nodes' is not namespace scoped

role.rbac.authorization.k8s.io/node-reader created
rolebinding.rbac.authorization.k8s.io/node-reader created
Warning: resource 'nodes' is not namespace scoped

yes
Error from server (Forbidden): nodes is forbidden: User "jai" cannot list resource "nodes" in API group "" at the cluster scope
The right way: a ClusterRole
# Remove the mistaken Role and RoleBinding
kubectl delete role,rolebinding node-reader -n default
# Create a ClusterRole that can read nodes
kubectl create clusterrole node-reader --verb=get,list --resource=nodes
# Bind it to jai with a ClusterRoleBinding
kubectl create clusterrolebinding node-reader --clusterrole=node-reader --user=jai
# List nodes as jai — now it works
kubectl --context jai get nodes
Expected output
role.rbac.authorization.k8s.io "node-reader" deleted from default namespace
rolebinding.rbac.authorization.k8s.io "node-reader" deleted from default namespace
clusterrole.rbac.authorization.k8s.io/node-reader created
clusterrolebinding.rbac.authorization.k8s.io/node-reader created
NAME                STATUS   ROLES           AGE   VERSION
lab-control-plane   Ready    control-plane   11h   v1.37.0
lab-worker          Ready    <none>          11h   v1.37.0
lab-worker2         Ready    <none>          11h   v1.37.0
What just happened
  • Nodes, PersistentVolumes, Namespaces and StorageClasses don't live in any namespace. A Role — always inside one namespace — can't reach them.
  • Kubernetes accepted the useless Role with only a warning. Then can-i said yes, because it checked the namespace default, where the Role matched. The real request is cluster-scoped, and was Forbidden.
  • Lesson: read warnings, and confirm with a real command. The fix is a ClusterRole with a ClusterRoleBinding.
  • The kubectl create role/clusterrole/…binding shortcuts are handy for quick tests. For anything you keep, write YAML and put it in Git.
Checkpoint
The Role gave a warning, a misleading yes and a real Forbidden; the ClusterRole let jai list the three nodes.
7

Teams: a built-in ClusterRole, bound to a group, in one namespace

Slides 8, 24, 29~6 min

Goal: Give everyone in group developers read-only access to namespace dev, using the ready-made view role.

Run from: module9-lab/
Creates: dev-team.yaml
# Create the YAML that grants the built-in view ClusterRole to a group inside one namespace
cat > dev-team.yaml <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: developers-view
  namespace: dev                   # the grant only counts in namespace dev
subjects:
  - kind: Group
    name: developers               # everyone whose certificate says O=developers
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole                # reuse a built-in ClusterRole …
  name: view                       # … read-only access to most namespaced objects
  apiGroup: rbac.authorization.k8s.io
EOF
Terminal
# Create the dev namespace
kubectl create namespace dev
# Apply the RoleBinding in dev
kubectl apply -f dev-team.yaml
# Check several actions in dev and default to see what the group may do
for q in "list deployments -n dev" "list configmaps -n dev" "list secrets -n dev" "create deployments -n dev" "list deployments -n default"; do echo "$q: $(kubectl auth can-i $q --as=jai --as-group=developers)"; done
# Check as jai without the group — no access, because groups come from the certificate
echo "without --as-group: $(kubectl auth can-i list deployments -n dev --as=jai)"
# Read ConfigMaps in dev as jai, using the developers group from the certificate
kubectl --context jai get configmaps -n dev
Expected output
namespace/dev created
rolebinding.rbac.authorization.k8s.io/developers-view created
list deployments -n dev: yes
list configmaps -n dev: yes
list secrets -n dev: no
create deployments -n dev: no
list deployments -n default: no
without --as-group: no
NAME               DATA   AGE
kube-root-ca.crt   1      1s
The built-in roles
# Compare the built-in ClusterRoles view, edit, admin and cluster-admin
kubectl get clusterroles view edit admin cluster-admin
# Show how the view role is built by aggregating other roles
kubectl get clusterrole view -o jsonpath='{.aggregationRule}'; echo
Expected output
NAME            CREATED AT
view            2026-09-29T04:43:11Z
edit            2026-09-29T04:43:11Z
admin           2026-09-29T04:43:11Z
cluster-admin   2026-09-29T04:43:11Z
{"clusterRoleSelectors":[{"matchLabels":{"rbac.authorization.k8s.io/aggregate-to-view":"true"}}]}
What just happened
  • A RoleBinding can point at a ClusterRole. The rules come from the ClusterRole, the reach stays inside the binding's namespace. Write the rules once, reuse them in many namespaces — the most common pattern in real clusters.
  • Binding to a Group means you manage people in your identity system (the certificate's O, or an OIDC group), not in Kubernetes. Someone joins the team → they get access. They leave → it's gone.
  • view reads most things but not Secrets — on purpose. edit can change workloads, admin can also manage RBAC in the namespace, cluster-admin is everything.
  • Gotcha: --as=jai alone doesn't include jai's groups — it answered no. Add --as-group=developers, or test with the real --context jai.
  • aggregationRule: view is assembled from every ClusterRole with a certain label. Installing an add-on can extend view automatically.
Checkpoint
With the group, deployments and configmaps yes, secrets and create no, and nothing in default.
8

RBAC stops privilege escalation

Slides 20, 29, 33~5 min

Goal: Let jai manage Roles in dev, then watch jai fail to grant more access than jai already has.

Run from: module9-lab/
Creates: role-manager.yaml
# Create the YAML for a Role that lets someone manage Roles in dev
cat > role-manager.yaml <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: role-manager
  namespace: dev
rules:
  - apiGroups: ["rbac.authorization.k8s.io"]
    resources: ["roles", "rolebindings"]
    verbs: ["get", "list", "create", "update", "delete"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: jai-role-manager
  namespace: dev
subjects:
  - kind: User
    name: jai
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: role-manager
  apiGroup: rbac.authorization.k8s.io
EOF
Terminal
# Create the role-manager Role
kubectl apply -f role-manager.yaml
# Print a label for the first escalation test
echo '--- a Role jai could already use:'
# Create a Role jai already has the rights for — allowed
kubectl --context jai -n dev create role cm-reader --verb=get,list --resource=configmaps
# Print a label for the second escalation test
echo '--- a Role for Secrets (jai has no Secret access):'
# Try to create a Role for Secrets — denied, you can't grant what you don't have
kubectl --context jai -n dev create role secret-reader --verb=get,list --resource=secrets 2>&1 | head -2
# Print a label for the third escalation test
echo '--- bind jai to admin:'
# Try to bind jai to the admin ClusterRole — denied, same escalation rule
kubectl --context jai -n dev create rolebinding jai-admin --clusterrole=admin --user=jai 2>&1 | head -2
Expected output
role.rbac.authorization.k8s.io/role-manager created
rolebinding.rbac.authorization.k8s.io/jai-role-manager created
--- a Role jai could already use:
role.rbac.authorization.k8s.io/cm-reader created
--- a Role for Secrets (jai has no Secret access):
Error from server (Forbidden): roles.rbac.authorization.k8s.io "secret-reader" is forbidden: user "jai" (groups=["developers" "system:authenticated"]) is attempting to grant RBAC permissions not currently held:
{APIGroups:[""], Resources:["secrets"], Verbs:["get" "list"]}
--- bind jai to admin:
error: failed to create rolebinding: rolebindings.rbac.authorization.k8s.io "jai-admin" is forbidden: user "jai" (groups=["developers" "system:authenticated"]) is attempting to grant RBAC permissions not currently held:
{APIGroups:[""], Resources:["configmaps"], Verbs:["create" "delete" "deletecollection" "patch" "update"]}
What just happened
  • Being allowed to create Roles doesn't let you create any Role. You can only grant permissions you already hold. That's RBAC's built-in escalation check.
  • jai could create a configmap reader (jai can read configmaps through view), but not a Secret reader, and not bind jai's own account to admin — the error lists every permission jai would be sneaking in.
  • Two verbs deliberately skip this check: escalate (on roles) and bind (on a role reference). Treat them like cluster-admin — give them to almost nobody.
  • Also dangerous: create pods (a Pod can run as any ServiceAccount in its namespace), impersonate, and reading Secrets.
Checkpoint
cm-reader was created; secret-reader and jai-admin were refused with attempting to grant RBAC permissions not currently held.

9

A ServiceAccount for a Pod

Slides 19–22, 30~6 min

Goal: Give a Pod its own identity and look at the short-lived token Kubernetes mounts for it.

Run from: module9-lab/
Creates: serviceaccount.yaml — the account and its RoleBinding to pod-reader
# Create the YAML for a ServiceAccount, with a Role and RoleBinding for it
cat > serviceaccount.yaml <<'EOF'
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-reader
  namespace: default
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app-reader-binding
  namespace: default
subjects:
  - kind: ServiceAccount
    name: app-reader
    namespace: default
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
EOF
Creates: app-reader-pod.yaml
# Create the YAML for a Pod that runs as that ServiceAccount
cat > app-reader-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: api-client
  namespace: default
spec:
  serviceAccountName: app-reader     # the Pod's identity when it calls the API
  containers:
    - name: app
      image: nginx:1.28-alpine       # has curl, which we use to call the API
      ports:
        - containerPort: 80
EOF
Terminal
# Create the ServiceAccount and the Pod
kubectl apply -f serviceaccount.yaml -f app-reader-pod.yaml
# List the ServiceAccounts in default
kubectl get serviceaccounts
# Wait until the Pod is Ready
kubectl wait --for=condition=Ready pod/api-client --timeout=60s
# Show the Pod's ServiceAccount and the token mount path
kubectl describe pod api-client | grep -E 'Service Account|/var/run/secrets'
# Show the projected, auto-rotating token settings in the Pod spec
kubectl get pod api-client -o jsonpath='{.spec.volumes[?(@.projected)].projected.sources[0].serviceAccountToken}'; echo
Expected output
serviceaccount/app-reader created
rolebinding.rbac.authorization.k8s.io/app-reader-binding created
pod/api-client created
NAME         AGE
app-reader   0s
default      11h
pod/api-client condition met
Service Account:  app-reader
      /var/run/secrets/kubernetes.io/serviceaccount from kube-api-access-fgb4r (ro)
{"expirationSeconds":3607,"path":"token"}
What does the token say?
# Decode the token's payload inside the Pod and show its subject and audience
kubectl exec api-client -- sh -c '
P=$(cut -d. -f2 /var/run/secrets/kubernetes.io/serviceaccount/token | tr "_-" "/+")
while [ $((${#P} % 4)) -ne 0 ]; do P="$P="; done   # JWTs drop base64 padding
echo "$P" | base64 -d' | tr ',' '\n' | grep -E '"(sub|aud)"'
Expected output
{"aud":["https://kubernetes.default.svc.cluster.local"]
"sub":"system:serviceaccount:default:app-reader"}
What just happened
  • A ServiceAccount is an identity for programs, not people. Every namespace has one called default; Pods use it unless you name another.
  • No SECRETS column any more: tokens aren't stored as Secret objects. The kubelet asks for a fresh token (expirationSeconds: 3607 ≈ 1 hour) through the TokenRequest API, mounts it, and renews it before it expires.
  • The token is a signed JWT. Its subject is system:serviceaccount:default:app-reader — that's the name RBAC sees.
  • Give each app its own ServiceAccount with only the rules it needs. Never add rights to default: every Pod that forgets to set an account would get them.
Checkpoint
The Pod runs as app-reader, has a projected token mounted, and the token's sub is system:serviceaccount:default:app-reader.
10

Call the API from inside the Pod

Slides 23, 30~5 min

Goal: Use the mounted token the way an app or controller would: list Pods, then try what isn't allowed.

Run from: module9-lab/
Terminal
# Check what the ServiceAccount may do, impersonating it
echo "can-i: $(kubectl auth can-i list pods --as=system:serviceaccount:default:app-reader) / $(kubectl auth can-i delete pods --as=system:serviceaccount:default:app-reader)"
# Call the API server from inside the Pod using its token to list, delete and read Secrets
kubectl exec api-client -- sh -c '
SA=/var/run/secrets/kubernetes.io/serviceaccount
AUTH="Authorization: Bearer $(cat $SA/token)"
API=https://kubernetes.default.svc/api/v1/namespaces/default
echo "--- list pods:";   curl -s --cacert $SA/ca.crt -H "$AUTH" $API/pods | grep -c "\"phase\""
echo "--- delete web:";  curl -s --cacert $SA/ca.crt -H "$AUTH" -X DELETE $API/pods/web | grep -E "\"(message|code)\""
echo "--- list secrets:"; curl -s --cacert $SA/ca.crt -H "$AUTH" $API/secrets | grep -E "\"(message|code)\""'
Expected output
can-i: yes / no
--- list pods:
2
--- delete web:
  "message": "pods \"web\" is forbidden: User \"system:serviceaccount:default:app-reader\" cannot delete resource \"pods\" in API group \"\" in the namespace \"default\"",
  "code": 403
--- list secrets:
  "message": "secrets is forbidden: User \"system:serviceaccount:default:app-reader\" cannot list resource \"secrets\" in API group \"\" in the namespace \"default\"",
  "code": 403
What just happened
  • This is what every controller, operator and CI tool in a cluster does: read the mounted token, call https://kubernetes.default.svc, and trust the cluster's CA from ca.crt.
  • Listing Pods worked (2 Pods). Deleting a Pod and listing Secrets returned 403 Forbidden — the same decision can-i predicted with the impersonation name system:serviceaccount:<namespace>:<name>.
  • If someone breaks into this Pod, the stolen token can only read Pods in one namespace. That's least privilege paying off.
Checkpoint
list pods returned a count, and both other calls returned 403.
11

No API calls? No token

Slides 20, 30~3 min

Goal: Switch the token off for a Pod that never talks to the API.

Run from: module9-lab/
Creates: no-token-pod.yaml
# Create the YAML for a Pod that opts out of the API token
cat > no-token-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: no-api-needed
spec:
  automountServiceAccountToken: false   # this app never calls the API: no token at all
  containers:
    - name: web
      image: nginx:1.28-alpine
EOF
Terminal
# Create the no-token Pod
kubectl apply -f no-token-pod.yaml
# Wait until the no-token Pod is Ready
kubectl wait --for=condition=Ready pod/no-api-needed --timeout=60s
# Show the token folder does not exist in the no-token Pod
echo '--- no-api-needed:'; kubectl exec no-api-needed -- ls /var/run/secrets/kubernetes.io/serviceaccount
# Show the token folder does exist in a default Pod
echo '--- web (default settings):'; kubectl exec web -- ls /var/run/secrets/kubernetes.io/serviceaccount
Expected output
pod/no-api-needed created
pod/no-api-needed condition met
--- no-api-needed:
ls: /var/run/secrets/kubernetes.io/serviceaccount: No such file or directory
command terminated with exit code 1
--- web (default settings):
ca.crt
namespace
token
What just happened
  • By default every Pod gets a token — even a web server that never calls the API. That's a free credential for an attacker.
  • automountServiceAccountToken: false on the Pod (or on the ServiceAccount) removes it. Nothing to steal.
  • A good default for app teams: turn it off everywhere, and turn it on only for Pods that really use the API.
Checkpoint
no-api-needed has no token folder; web has ca.crt, namespace, token.

Pod Security Admission: RBAC says who, PSA says what

Slides 31–32~8 min

Goal: Label a namespace restricted, watch unsafe Pods get rejected — including Module 8's hostPath Pod — and admit a hardened one.

Run from: module9-lab/
Creates: secure-namespace.yaml
# Create the YAML for a namespace that enforces the restricted Pod Security level
cat > secure-namespace.yaml <<'EOF'
apiVersion: v1
kind: Namespace
metadata:
  name: secure
  labels:
    pod-security.kubernetes.io/enforce: restricted      # reject Pods that break the rules
    pod-security.kubernetes.io/enforce-version: latest
EOF
Creates: hostpath-in-secure.yaml — a Pod that mounts the whole node
# Create the YAML for a Pod that mounts the node's filesystem
cat > hostpath-in-secure.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: node-snooper
  namespace: secure
spec:
  volumes:
    - name: host
      hostPath:
        path: /                       # the whole node's disk
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]
      volumeMounts:
        - name: host
          mountPath: /host
EOF
Try two unsafe Pods
# Create the secure namespace
kubectl apply -f secure-namespace.yaml
# Try to run the hostPath Pod in secure — rejected by Pod Security
kubectl apply -f hostpath-in-secure.yaml
# Try to run a plain nginx Pod in secure — rejected, it isn't hardened
kubectl -n secure run plain-nginx --image=nginx:1.28-alpine
Expected output
namespace/secure created
Error from server (Forbidden): error when creating "hostpath-in-secure.yaml": pods "node-snooper" is forbidden: violates PodSecurity "restricted:latest": allowPrivilegeEscalation != false (container "app" must set securityContext.allowPrivilegeEscalation=false), unrestricted capabilities (container "app" must set securityContext.capabilities.drop=["ALL"]), restricted volume types (volume "host" uses restricted volume type "hostPath"), runAsNonRoot != true (pod or container "app" must set securityContext.runAsNonRoot=true), seccompProfile (pod or container "app" must set securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")
Error from server (Forbidden): pods "plain-nginx" is forbidden: violates PodSecurity "restricted:latest": allowPrivilegeEscalation != false (…), unrestricted capabilities (…), runAsNonRoot != true (…), seccompProfile (…)
Creates: restricted-pod.yaml — a Pod that follows every rule
# Create the YAML for a hardened Pod that meets the restricted level
cat > restricted-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: good-citizen
  namespace: secure
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
EOF
# Create the hardened Pod
kubectl apply -f restricted-pod.yaml
# Wait until the hardened Pod is Ready
kubectl -n secure wait --for=condition=Ready pod/good-citizen --timeout=60s
# Show the Pod runs as a non-root user
kubectl -n secure exec good-citizen -- id
Expected output
pod/good-citizen created
pod/good-citizen condition met
uid=1000 gid=0(root) groups=0(root)
Would my existing namespace pass? Ask before enforcing
# Preview what enforcing restricted on default would warn about, without changing anything
kubectl label --dry-run=server --overwrite namespace default pod-security.kubernetes.io/enforce=restricted
Expected output
Warning: existing pods in namespace "default" violate the new PodSecurity enforce level "restricted:latest"
Warning: api-client (and 2 other pods): allowPrivilegeEscalation != false, unrestricted capabilities, runAsNonRoot != true, seccompProfile
namespace/default labeled (server dry run)
LevelIn one sentenceTypical use
privilegedno rules at allsystem namespaces: CNI, storage and monitoring agents
baselineblocks the known-dangerous things: hostPath, host network, privileged containersa safe default for most app namespaces
restrictedbaseline + non-root, no privilege escalation, drop all capabilities, seccompanything that faces the internet or handles sensitive data
What just happened
  • RBAC decides who may create a Pod. Pod Security Admission decides what a Pod may do. You need both: jai with edit in dev could otherwise create a hostPath Pod and read the node's disk.
  • It's built into the API server (stable since v1.25) and configured with namespace labels. The error lists every rule the Pod breaks — a to-do list for your YAML.
  • Plain nginx fails restricted because it starts as root. Production teams use images built to run as a normal user.
  • Roll it out safely: labels warn and audit report without blocking, and --dry-run=server shows which running Pods would fail before you switch to enforce.
Checkpoint
node-snooper and plain-nginx were rejected, good-citizen runs as uid=1000, and the dry run warned about the Pods in default.

Clean up

—~3 min

Goal: Remove the namespaces, Pods, RBAC objects, the CSR and jai's kubeconfig entries. Keep the cluster for Module 10.

Run from: module9-lab/
Terminal
# Delete the dev and secure namespaces
kubectl delete namespace dev secure
# Delete the lab Pods
kubectl delete pod web api-client no-api-needed --now
# Delete the ServiceAccount, RoleBinding and Role
kubectl delete -f serviceaccount.yaml -f rolebinding.yaml -f role.yaml
# Delete the ClusterRoleBinding and ClusterRole
kubectl delete -f clusterrolebinding.yaml -f clusterrole.yaml
# Delete the node-reader ClusterRoleBinding
kubectl delete clusterrolebinding node-reader
# Delete the node-reader ClusterRole
kubectl delete clusterrole node-reader
# Delete jai's certificate signing request
kubectl delete csr jai
# Remove the jai context from your kubeconfig
kubectl config delete-context jai
# Remove the jai user from your kubeconfig
kubectl config delete-user jai
# Delete jai's local key and certificate files
rm -f jai.key jai.csr jai.crt
# Confirm no lab resources remain
kubectl get all
# Confirm your kubeconfig is back to the original contexts
kubectl config get-contexts
Expected output
namespace "dev" deleted
namespace "secure" deleted
pod "web" deleted from default namespace
…
certificatesigningrequest.certificates.k8s.io "jai" deleted
deleted context jai from /home/you/.kube/config
deleted user jai from /home/you/.kube/config
NAME                 TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)   AGE
service/kubernetes   ClusterIP   10.96.0.1    <none>        443/TCP   11h
CURRENT   NAME       CLUSTER    AUTHINFO   NAMESPACE
*         kind-lab   kind-lab   kind-lab   default
What just happened
  • Deleting a namespace deletes its Roles and RoleBindings. ClusterRoles, ClusterRoleBindings and CSRs are cluster-scoped, so they go one by one.
  • Deleting the kubeconfig entry doesn't revoke the certificate — it stays valid until it expires (we set one day). That's why short certificates, or OIDC logins, are the norm; to cut someone off now, remove their RBAC bindings.
  • jai.key is a private key. Delete it; never commit keys to Git.
  • Module 10 starts from this same cluster. To remove it completely: kind delete cluster --name lab.
Checkpoint
kubectl get all shows only service/kubernetes, and only the kind-lab context is left.

Troubleshooting

Error from server (Forbidden): … cannot list resource …
Authorization said no. Ask the exact question as admin: kubectl auth can-i <verb> <resource> -n <ns> --as=<user>, then check the RoleBinding's subject spelling and namespace (Steps 3–4).
A Role exists but access is still denied
No RoleBinding, a binding in another namespace, or a typo in subjects. kubectl get rolebindings -n <ns> -o wide shows who is bound to what.
can-i says yes, the real command says Forbidden
Cluster-scoped resource checked in a namespace (Step 6), pods/log instead of --subresource=log (Step 4), or groups missing from --as (add --as-group, Step 7).
error: You must be logged in to the server (Unauthorized) as jai
Authentication failed: the certificate expired (one day) or doesn't match the key. Create a new CSR (Step 2).
The CSR stays Pending
Someone with rights must run kubectl certificate approve jai. Denied or Failed: delete it and create a new one.
attempting to grant RBAC permissions not currently held
Escalation prevention (Step 8): you can only grant what you have. An admin must create that Role or binding.
A Pod is rejected with violates PodSecurity
The namespace enforces baseline or restricted. Fix each item in the message (runAsNonRoot, drop ALL, seccomp, no hostPath), or use a namespace with a lower level (Step 12).
kind load fails with ctr: content digest sha256:… not found
Docker 29 keeps images in its containerd image store: it downloads only your platform, but docker save still lists all of them, and kind's import looks for every one. Save just your platform and load the archive — that's what the pre-load commands at the top of this page do: docker save --platform "$(docker version --format '{{.Server.Os}}/{{.Server.Arch}}')" -o image.tar IMAGE then kind load image-archive image.tar --name lab. Images you built yourself (like module1-demo-api) load fine with kind load docker-image.
ERROR: unknown containerd config version: 4 from kind
Your kind binary is older than the node image. Install kind v0.33 or newer (Module 2, Step 1) and run kind version to check.
