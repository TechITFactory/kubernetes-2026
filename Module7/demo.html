Requests and limits — what the scheduler reserves

Slides 3–6, 38~6 min

Goal: Run a Pod with requests and limits, read them back, and see the request booked on the node.

Run from: module7-lab/
Creates: resource-limited-pod.yaml
cat > resource-limited-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: resource-limited-pod
spec:
  containers:
    - name: busybox
      image: busybox:1.37
      command: ["sh", "-c", "while true; do echo Running...; sleep 5; done"]
      resources:
        requests:
          cpu: "500m"
          memory: "256Mi"
        limits:
          cpu: "1"
          memory: "512Mi"
EOF
Terminal
kubectl apply -f resource-limited-pod.yaml
kubectl wait --for=condition=Ready pod/resource-limited-pod --timeout=60s
kubectl describe pod resource-limited-pod | grep -E -A3 '^    (Limits|Requests):|^QoS'
Expected output
pod/resource-limited-pod created
pod/resource-limited-pod condition met
    Limits:
      cpu:     1
      memory:  512Mi
    Requests:
      cpu:        500m
      memory:     256Mi
    Environment:  <none>
--
QoS Class:                   Burstable
What the node has promised away
NODE=$(kubectl get pod resource-limited-pod -o jsonpath='{.spec.nodeName}')
echo "$NODE"
kubectl describe node "$NODE" | grep -A5 'Allocated resources'
Expected output
lab-worker
Allocated resources:
  (Total limits may be over 100 percent, i.e., overcommitted.)
  Resource           Requests    Limits
  --------           --------    ------
  cpu                600m (15%)  1 (25%)
  memory             306Mi (1%)  512Mi (3%)
What just happened
  • Requests are a booking. The scheduler adds up the requests of every Pod on a node and only places a new Pod where its request still fits. 600m = our 500m + 100m for the node's network agent (kindnet).
  • Limits are a ceiling the kubelet and the Linux kernel enforce while the container runs.
  • The booking happens even if the Pod sleeps all day. Requests that are too high waste nodes; requests that are too low overload them.
  • "Total limits may be over 100 percent": limits can be overcommitted, requests can't. That's why requests decide placement.
Checkpoint
Requests 500m / 256Mi, Limits 1 / 512Mi, and the node shows the request in Allocated resources.

QoS classes: who is evicted first

Slides 6, 9–10, 38~5 min

Goal: Create one Pod of each Quality of Service class and read the class Kubernetes gives it.

Run from: module7-lab/
Creates: qos-pods.yaml — three Pods
cat > qos-pods.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: qos-guaranteed
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]
      resources:
        requests: { cpu: 100m, memory: 64Mi }
        limits:   { cpu: 100m, memory: 64Mi }   # limits = requests
---
apiVersion: v1
kind: Pod
metadata:
  name: qos-burstable
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]
      resources:
        requests: { cpu: 100m, memory: 64Mi }   # limits higher, or missing
        limits:   { cpu: 500m, memory: 128Mi }
---
apiVersion: v1
kind: Pod
metadata:
  name: qos-besteffort
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]              # no resources at all
EOF
Terminal
kubectl apply -f qos-pods.yaml
kubectl wait --for=condition=Ready pod/qos-guaranteed pod/qos-burstable pod/qos-besteffort --timeout=60s >/dev/null
kubectl get pods -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass
Expected output
pod/qos-guaranteed created
pod/qos-burstable created
pod/qos-besteffort created
NAME                   QOS
qos-besteffort         BestEffort
qos-burstable          Burstable
qos-guaranteed         Guaranteed
resource-limited-pod   Burstable
ClassRuleWhen the node runs out of memory
Guaranteedevery container: requests = limits, for CPU and memoryevicted last
Burstableat least one request or limit, but not Guaranteedin between
BestEffortno requests or limits at allevicted first
What just happened
  • You never set the class yourself — Kubernetes derives it from requests and limits.
  • When a node runs short of memory, the kubelet evicts BestEffort Pods first and Guaranteed Pods last. Important databases often run as Guaranteed.
  • BestEffort Pods also book nothing, so the scheduler can pack them anywhere — that's how one noisy Pod starves its neighbours (slide 3).
Checkpoint
One Pod in each class: Guaranteed, Burstable, BestEffort.

CPU over the limit: throttled, not killed

Slides 7–8, 39~4 min

Goal: Run a busy loop with a 200m CPU limit and watch the kernel hold it there.

Run from: module7-lab/
Creates: cpu-hog.yaml
cat > cpu-hog.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: cpu-hog
spec:
  containers:
    - name: hog
      image: busybox:1.37
      command: ["sh", "-c", "while true; do :; done"]   # burns as much CPU as it can
      resources:
        requests: { cpu: 100m, memory: 16Mi }
        limits:   { cpu: 200m, memory: 32Mi }
EOF
Wait a minute for metrics, then look
kubectl apply -f cpu-hog.yaml
kubectl wait --for=condition=Ready pod/cpu-hog --timeout=60s >/dev/null
sleep 60
kubectl top pod cpu-hog
kubectl exec cpu-hog -- sh -c 'grep -hE "nr_periods|nr_throttled" /sys/fs/cgroup/cpu.stat /sys/fs/cgroup/cpu/cpu.stat 2>/dev/null; true'
kubectl get pod cpu-hog
Expected output
pod/cpu-hog created
NAME      CPU(cores)   MEMORY(bytes)
cpu-hog   200m         0Mi
nr_periods 418
nr_throttled 418
NAME      READY   STATUS    RESTARTS   AGE
cpu-hog   1/1     Running   0          61s
What just happened
  • The loop wants a whole CPU, but kubectl top shows 200m — exactly the limit.
  • The kernel splits time into 100 ms periods and gives the container 20 ms of CPU in each. nr_throttled counts the periods where it hit the ceiling and had to wait — here, every single one.
  • The container keeps running with 0 restarts. CPU is compressible: too little just makes the app slow. That's why slow responses with CPU at the limit point to throttling.
  • The command reads /sys/fs/cgroup/cpu.stat (cgroup v2, every current distribution — Module 2) or /sys/fs/cgroup/cpu/cpu.stat (old cgroup v1 hosts), whichever exists.
Checkpoint
CPU at 200m, nr_throttled growing, and RESTARTS 0.

Memory over the limit: OOMKilled

Slides 8, 39~4 min

Goal: Let a container grab memory until it hits its 64Mi limit, and read the evidence.

Run from: module7-lab/
Creates: memory-hog.yaml
cat > memory-hog.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: memory-hog
spec:
  containers:
    - name: hog
      image: busybox:1.37
      # tail keeps the "last line" in memory — /dev/zero has no newlines, so it grows forever
      command: ["sh", "-c", "echo starting; tail /dev/zero"]
      resources:
        requests: { cpu: 50m, memory: 64Mi }
        limits:   { cpu: 200m, memory: 64Mi }
EOF
Terminal
kubectl apply -f memory-hog.yaml
sleep 30
kubectl get pod memory-hog
kubectl describe pod memory-hog | grep -E -A3 'Last State'
kubectl get pod memory-hog -o jsonpath='{.status.containerStatuses[0].restartCount}{"\n"}'
Expected output
pod/memory-hog created
NAME         READY   STATUS      RESTARTS      AGE
memory-hog   0/1     OOMKilled   2 (25s ago)   30s
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
      Started:      Tue, 29 Sep 2026 10:32:53 +0000
2
What just happened
  • Memory is not compressible. When the container goes over its limit, the kernel's OOM killer stops it: OOMKilled, exit code 137 (128 + signal 9, SIGKILL).
  • The Pod's restartPolicy: Always restarts it. It fills up again and is killed again — soon you'll see CrashLoopBackOff.
  • The fix is never "more CPU". Either the limit is too low for the real workload, or the app leaks memory. Check kubectl top and the app's own metrics.
  • Remember the pair from slide 8: CPU limit = throttle, memory limit = kill.
Checkpoint
OOMKilled, exit code 137, and a restart count above 0.

A request no node can satisfy

Slides 4, 32, 39~3 min

Goal: Ask for more CPU than any node has and read the scheduler's reason.

Run from: module7-lab/
Creates: too-big.yaml
cat > too-big.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: too-big
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]
      resources:
        requests:
          cpu: "8"          # more than any single node can offer
          memory: 64Mi
EOF
Terminal
kubectl apply -f too-big.yaml
sleep 5
kubectl get pod too-big
kubectl get events --field-selector involvedObject.name=too-big,reason=FailedScheduling -o jsonpath='{.items[-1:].message}{"\n"}'
Expected output
pod/too-big created
NAME      READY   STATUS    RESTARTS   AGE
too-big   0/1     Pending   0          5s
0/3 nodes are available: 1 node(s) had untolerated taint(s), 2 Insufficient cpu. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.
What just happened
  • Each node has 4 CPUs. A request of 8 fits nowhere, so the Pod stays Pending forever — it's not an error, it's waiting.
  • Read the message node by node: the control plane has a taint the Pod doesn't tolerate (Part E), and the two workers have Insufficient cpu.
  • preemption: the scheduler could evict lower-priority Pods to make room, but that wouldn't help here. PriorityClasses control who may preempt whom.
  • On a cloud cluster, this is exactly the Pending Pod that makes a node autoscaler add a bigger node (Module 5).
Checkpoint
too-big is Pending with Insufficient cpu.

A container runs as root by default

Slide 11~4 min

Goal: Start a plain Pod and see who it runs as, and what it can change.

Run from: module7-lab/
Creates: sc-root.yaml
cat > sc-root.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: sc-root
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]
EOF
Terminal
kubectl apply -f sc-root.yaml
kubectl wait --for=condition=Ready pod/sc-root --timeout=60s
kubectl exec sc-root -- id
kubectl exec sc-root -- sh -c 'echo hello > /etc/motd && echo "wrote to /etc/motd"'
Expected output (key lines — spacing will differ)
pod/sc-root created
pod/sc-root condition met
uid=0(root) gid=0(root) groups=...
wrote to /etc/motd
What just happened
  • The file has no securityContext, so nothing limits the container.
  • uid=0(root): the process runs as root, even though we never asked for it.
  • Root can change files inside the container, here /etc/motd. That is the container's own copy, not the node's.
  • If someone breaks into this app, they get the same freedom. The next step takes it away.
Checkpoint
id shows uid=0(root) and the write to /etc/motd works.

Three safe settings in one Pod

Slides 12–13~6 min

Goal: Run the same app with the three safe rules and test each one.

Run from: module7-lab/
Creates: sc-safe.yaml
cat > sc-safe.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: sc-safe
spec:
  securityContext:
    runAsNonRoot: true          # rule 1: not root
    runAsUser: 1000
    runAsGroup: 3000            # the group it runs as
    fsGroup: 2000               # volumes get this group
    seccompProfile:
      type: RuntimeDefault      # one extra safety line
  volumes:
    - name: tmp
      emptyDir: {}
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]
      securityContext:
        readOnlyRootFilesystem: true       # rule 2: cannot change files
        allowPrivilegeEscalation: false    # rule 3: no extra powers
        capabilities:
          drop: ["ALL"]
      volumeMounts:
        - name: tmp
          mountPath: /tmp                  # the one folder it may write to
EOF
Terminal
kubectl apply -f sc-safe.yaml
kubectl wait --for=condition=Ready pod/sc-safe --timeout=60s
echo "--- rule 1: who am I?"
kubectl exec sc-safe -- id
echo "--- fsGroup: who owns the volume folder?"
kubectl exec sc-safe -- ls -ld /tmp
echo "--- rule 2: change a file"
kubectl exec sc-safe -- touch /hello
kubectl exec sc-safe -- sh -c 'touch /tmp/hello && echo "wrote to /tmp"'
echo "--- rule 3: any extra powers?"
kubectl exec sc-safe -- sh -c 'grep -E "^(CapEff|NoNewPrivs)" /proc/1/status'
Expected output (key lines — spacing will differ)
pod/sc-safe created
pod/sc-safe condition met
--- rule 1: who am I?
uid=1000 gid=3000 ...
--- fsGroup: who owns the volume folder?
drwxrwsrwx    2 root     2000   ...  /tmp
--- rule 2: change a file
touch: /hello: Read-only file system
command terminated with exit code 1
wrote to /tmp
--- rule 3: any extra powers?
CapEff:	0000000000000000
NoNewPrivs:	1
What just happened
  • Rule 1, runAsNonRoot, runAsUser: 1000 and runAsGroup: 3000: id now shows user 1000 and group 3000, not root.
  • fsGroup: 2000 is for volumes. The mounted folder /tmp belongs to group 2000, and there is an s in the permissions (setgid), so files created there keep that group. This is the usual fix when an app says "permission denied" on a mounted volume.
  • Rule 2, readOnlyRootFilesystem: creating /hello fails with Read-only file system. But /tmp works, because we mounted an emptyDir there. Give the app a writable folder only where it needs one.
  • Rule 3, allowPrivilegeEscalation: false and drop: ["ALL"]: CapEff is all zeros, which means no extra Linux powers. NoNewPrivs: 1 means it cannot get them later.
  • Pod level (under spec): runAsNonRoot, runAsUser, runAsGroup, fsGroup, seccompProfile. Container level (inside the container): readOnlyRootFilesystem, allowPrivilegeEscalation, capabilities. If both set the same field, the container wins.
  • seccompProfile: RuntimeDefault is one more safety line. We add it now because Step 9 needs it.
Checkpoint
sc-safe runs as user 1000 group 3000, /tmp belongs to group 2000, it cannot write to /, can write to /tmp, and CapEff is all zeros.

Startup, readiness and liveness in one Pod

Slides 14–21, 41~8 min

Goal: Watch one Pod go through all three probes: a slow start, ready, broken, restarted.

Run from: module7-lab/
Creates: probes-pod.yaml
cat > probes-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: probe-demo
spec:
  terminationGracePeriodSeconds: 5   # sh ignores SIGTERM — don't wait the default 30 s
  containers:
    - name: my-app
      image: busybox:1.37
      # ready after 30 s, "breaks" 30 s later by deleting the file
      command: ["/bin/sh", "-c", "sleep 30 && touch /tmp/ready && sleep 30 && rm -f /tmp/ready && sleep 600"]
      startupProbe:
        exec:
          command: ["cat", "/tmp/ready"]
        periodSeconds: 5
        failureThreshold: 12        # up to 60 s to finish booting
      readinessProbe:
        exec:
          command: ["cat", "/tmp/ready"]
        periodSeconds: 3
        failureThreshold: 2
      livenessProbe:
        exec:
          command: ["cat", "/tmp/ready"]
        periodSeconds: 5
        failureThreshold: 3
EOF
Watch for 90 seconds
kubectl apply -f probes-pod.yaml
timeout 90 kubectl get pod probe-demo -w
Expected output
pod/probe-demo created
NAME         READY   STATUS              RESTARTS   AGE
probe-demo   0/1     ContainerCreating   0          0s
probe-demo   0/1     Running             0          1s
probe-demo   0/1     Running             0          35s
probe-demo   1/1     Running             0          35s
probe-demo   0/1     Running             0          65s
probe-demo   0/1     Running             1 (1s ago)   81s
What the kubelet saw
kubectl get events --field-selector involvedObject.name=probe-demo \
  -o custom-columns=REASON:.reason,COUNT:.count,MESSAGE:.message | grep -E 'REASON|Unhealthy|Killing'
Expected output
REASON      COUNT   MESSAGE
Unhealthy   6       Startup probe failed: cat: can't open '/tmp/ready': No such file or directory
Unhealthy   3       Liveness probe failed: cat: can't open '/tmp/ready': No such file or directory
Killing     1       Container my-app failed liveness probe, will be restarted
Unhealthy   5       Readiness probe failed: cat: can't open '/tmp/ready': No such file or directory
TimeWhat happenedWhich probe
0–30 sREADY 0/1, startup probe fails every 5 s — but it may fail 12 timesstartup
~35 sfile exists → startup succeeds, then readiness passes → 1/1startup, readiness
~65 sfile removed → readiness fails → 0/1, still runningreadiness
~75 sliveness fails 3× → kubelet kills the container → RESTARTS 1liveness
What just happened
  • Until the startup probe succeeds, liveness and readiness don't run at all. That's how a slow app gets time to boot without being killed.
  • Readiness flips READY. Liveness changes RESTARTS. Watch those two columns and you always know which probe fired.
  • After the restart the story starts again from the top — the file is gone, so startup protection applies again.
  • The Pod waited 5 s before the restart because of terminationGracePeriodSeconds: 5. With the default 30 s you'd wait half a minute: sh as PID 1 ignores SIGTERM.
Checkpoint
READY went 0/1 → 1/1 → 0/1, then RESTARTS 1, and the events show all three probes.

Readiness takes a Pod out of the Service

Slides 16, 18, 41~6 min

Goal: Break one of two web Pods and prove that clients stop reaching it — without a restart.

Run from: module7-lab/
Creates: web-probes.yaml — Deployment + Service
cat > web-probes.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.28-alpine
          ports:
            - containerPort: 80
          readinessProbe:            # "can I take traffic?"
            httpGet:
              path: /
              port: 80
            periodSeconds: 3
            failureThreshold: 1
          livenessProbe:             # "is the process alive?" — a different, cheaper check

Troubleshooting

Pod stuck in CreateContainerConfigError: "image will run as root"
You set runAsNonRoot: true, but the image runs as root. Add runAsUser: 1000, or use an image built for a normal user.
permission denied when the app writes to a mounted volume
The volume belongs to a group the process is not in. Set fsGroup in the Pod's securityContext (Step 8).
Read-only file system after turning on readOnlyRootFilesystem
The app writes to a folder in its image (logs, cache, /tmp). Mount an emptyDir at that path (Step 8).
Pod rejected: violates PodSecurity "restricted:latest"
Add the lines the message lists: runAsNonRoot, allowPrivilegeEscalation: false, drop: ["ALL"], seccompProfile (Step 9).
error: Metrics API not available from kubectl top
metrics-server isn't installed or isn't ready yet. Install it (Step 1) and wait about 30 seconds.
A Pod stays Pending
Read the reason: kubectl get events --field-selector involvedObject.name=<pod>. Insufficient cpu/memory → lower the request (Step 6). didn't match … affinity/selector → label a node or relax the rule (Step 12). untolerated taint → add a toleration or remove the taint (Steps 16–17).
OOMKilled / exit code 137, restarts keep rising
The container used more memory than its limit. Raise the limit to fit real usage, or fix the leak (Step 5). More CPU won't help.
App is slow, CPU at exactly its limit in kubectl top
It's being throttled. Check nr_throttled in /sys/fs/cgroup/cpu.stat and raise or remove the CPU limit (Step 4).
Pod Running but 0/1 READY and no traffic
The readiness probe fails. kubectl describe pod shows Readiness probe failed: …. Fix the path/port or the dependency it checks (Step 11).
Container restarts every minute with failed liveness probe
The app starts slower than the liveness probe allows, or the probe is too strict. Add a startupProbe or relax periodSeconds/failureThreshold (Step 10).
Topology spread leaves Pods Pending although nodes have room
A tainted node (often the control plane) counts as an empty domain. Add nodeTaintsPolicy: Honor to the constraint (Step 15).
Nothing schedules on one node, weeks later
A forgotten taint. kubectl describe nodes | grep -A2 Taints, then remove it with kubectl taint nodes <node> <key>- (Step 17).
A Pod takes 30 seconds to delete
Its PID 1 ignores SIGTERM (for example sleep or sh). Use --now in labs; in real images handle SIGTERM or lower terminationGracePeriodSeconds.
kind load fails with ctr: content digest sha256:… not found
Docker 29 keeps images in its containerd image store: it downloads only your platform, but docker save still lists all of them, and kind's import looks for every one. Save just your platform and load the archive — that's what the pre-load commands at the top of this page do: docker save --platform "$(docker version --format '{{.Server.Os}}/{{.Server.Arch}}')" -o image.tar IMAGE then kind load image-archive image.tar --name lab. Images you built yourself (like module1-demo-api) load fine with kind load docker-image.
ERROR: unknown containerd config version: 4 from kind
Your kind binary is older than the node image. Install kind v0.33 or newer (Module 2, Step 1) and run kind version to check.
