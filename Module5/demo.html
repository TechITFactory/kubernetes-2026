Bootstrap tokens and the join command

Slides 4–7 · Quiz Q5~4 min

Goal: Look at the control plane's join tokens and print a fresh, ready-to-use join command.

Run from: module5-lab/
Run kubeadm on the control-plane node
docker exec lab-control-plane kubeadm token list
Expected output
TOKEN                     TTL   EXPIRES                USAGES                   DESCRIPTION   EXTRA GROUPS
abcdef.0123456789abcdef   20h   2026-09-30T04:43:12Z   authentication,signing   <none>        system:bootstrappers:kubeadm:default-node-token
A fresh join command, valid for 1 hour
docker exec lab-control-plane kubeadm token create --print-join-command --ttl 1h
Expected output
kubeadm join lab-control-plane:6443 --token 0pbaax.1ciutu1tiqmn2d42 --discovery-token-ca-cert-hash sha256:49953a3de3ce14f8aec05b990c8eec7bd94ed871aa669fc4f92e0c3e0e20a176
What just happened
  • A join command has three parts: the API server address, a bootstrap token (a short-lived password), and the CA certificate hash so the new node can trust it's talking to the right cluster.
  • Tokens expire — 24 hours by default. We asked for --ttl 1h. When a token has expired, kubeadm join keeps retrying with could not find a JWS signature … for token ID until it times out. The fix is always a fresh token create (Quiz Q5).
  • Treat tokens like passwords. Never paste a real production token into a ticket, a chat or a slide.
  • On a real server you'd run these commands on the control-plane host itself. We use docker exec because our control plane is a container.
Checkpoint
You have a kubeadm join … line with a token and a sha256: hash.

Cordon: stop new Pods, keep old ones

Goal: Run an app on every worker, cordon one node, and find out exactly what cordon does — and doesn't — stop.

Run from: module5-lab/
Creates: web.yaml — 6 replicas of nginx
cat > web.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels:
    app: web
spec:
  replicas: 6
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.28-alpine
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: 20m
              memory: 32Mi

              cpu: 100m

              path: /

Creates: pinned-pod.yaml and bare-pod.yaml
cat > pinned-pod.yaml <<'EOF'
apiVersion: v1

EOF

Expected output

What just happened
  • Cordon marks the node SchedulingDisabled by adding the taint node.kubernetes.io/unschedulable:NoSchedule.
  • The 2 Pods already on lab-worker kept running. The 3 new Pods went to the other workers.
  • pinned uses nodeSelector, which goes through the scheduler. The scheduler respects the cordon, so the Pod waits in Pending. The event explains every node: one unschedulable, one tainted (the control plane), two don't match.
  • bare uses nodeName, which skips the scheduler. The kubelet just runs it — cordon can't stop it (Quiz Q3). Avoid nodeName in real manifests.
Checkpoint

Drain: why it refuses

Slides 12–14, 24, 39 · Quiz Q2~4 min

Goal: Try to empty lab-worker with a plain drain and read the two reasons it refuses.

Run from: module5-lab/
Terminal
kubectl drain lab-worker
Expected output
node/lab-worker already cordoned
error: unable to drain node "lab-worker" due to error: [cannot delete Pods that declare no controller (use --force to override): default/bare, cannot delete DaemonSet-managed Pods (use --ignore-daemonsets to ignore): kube-system/kindnet-2b649, kube-system/kube-proxy-fnjlw], continuing command...
There are pending nodes to be drained:
 lab-worker
cannot delete Pods that declare no controller (use --force to override): default/bare
cannot delete DaemonSet-managed Pods (use --ignore-daemonsets to ignore): kube-system/kindnet-2b649, kube-system/kube-proxy-fnjlw
What just happened
  • Drain = cordon + evict every Pod on the node. It checked first and found two problems, so it evicted nothing.
  • DaemonSet Pods (kindnet, kube-proxy): evicting them is pointless — the DaemonSet would put them straight back on the same node. --ignore-daemonsets means "leave them, I know" (Quiz Q2).
  • A Pod with no controller (bare): nothing would recreate it anywhere. Evicting it deletes it for good, so kubectl makes you say --force.
  • A third flag you'll meet: --delete-emptydir-data, for Pods using emptyDir volumes — their scratch data is lost on eviction.
Checkpoint
The drain stopped with both error messages, and all Pods are still on lab-worker.

PodDisruptionBudgets: blocked drain, then a good one

Slides 13, 16, 39–40, 44 · Quiz Q1~8 min

Goal: See a too-strict PodDisruptionBudget block maintenance, then replace it with one that protects the app and lets the drain finish.

Run from: module5-lab/
Creates: web-pdb-strict.yaml — a common mistake
cat > web-pdb-strict.yaml <<'EOF'
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  maxUnavailable: 0          # anti-pattern: no voluntary disruption, ever
  selector:
    matchLabels:
      app: web
EOF
Terminal
kubectl apply -f web-pdb-strict.yaml
kubectl get pdb web-pdb
kubectl drain lab-worker --ignore-daemonsets --force --timeout=20s 2>&1 | grep -E 'evicting|Cannot evict|timeout' | head -4
Expected output
poddisruptionbudget.policy/web-pdb created
NAME      MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
web-pdb   N/A             0                 0                     0s
evicting pod default/web-766d5c7b8d-vfnnj
evicting pod default/bare
evicting pod default/web-766d5c7b8d-4nffq
error when evicting pods/"web-766d5c7b8d-vfnnj" -n "default" (will retry after 5s): Cannot evict pod as it would violate the pod's disruption budget.
Creates: web-pdb.yaml — the production version
cat > web-pdb.yaml <<'EOF'
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  maxUnavailable: 1                          # one Pod at a time may be evicted
  unhealthyPodEvictionPolicy: AlwaysAllow    # broken Pods never block a drain
  selector:
    matchLabels:
      app: web
EOF
Same drain, better budget
kubectl apply -f web-pdb.yaml
kubectl get pdb web-pdb
kubectl drain lab-worker --ignore-daemonsets --force --timeout=120s
kubectl get pods -l app=web -o custom-columns=NODE:.spec.nodeName --no-headers | sort | uniq -c
Expected output
poddisruptionbudget.policy/web-pdb configured
NAME      MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
web-pdb   N/A             1                 1                     25s
node/lab-worker already cordoned
Warning: ignoring DaemonSet-managed Pods: kube-system/kindnet-2b649, kube-system/kube-proxy-fnjlw
evicting pod default/web-766d5c7b8d-vfnnj
evicting pod default/web-766d5c7b8d-4nffq
error when evicting pods/"web-766d5c7b8d-vfnnj" -n "default" (will retry after 5s): Cannot evict pod as it would violate the pod's disruption budget.
pod/web-766d5c7b8d-4nffq evicted
evicting pod default/web-766d5c7b8d-vfnnj
pod/web-766d5c7b8d-vfnnj evicted
node/lab-worker drained
      5 lab-worker2
      4 lab-worker3
What just happened
  • A PodDisruptionBudget limits voluntary disruptions — drains, upgrades, autoscaler scale-downs. It can't stop a node from crashing.
  • maxUnavailable: 0 (or minAvailable equal to the replica count) means "never evict anything". ALLOWED DISRUPTIONS = 0, so the drain retries every 5 seconds forever. We stopped it with --timeout (Quiz Q1).
  • maxUnavailable: 1 lets the drain move one Pod at a time: evict, wait for the replacement to be ready elsewhere, evict the next. Look for that single retry in the output.
  • unhealthyPodEvictionPolicy: AlwaysAllow (stable) lets a drain evict Pods that are Running but not Ready. Without it, an already-broken app can block node maintenance.
  • The first attempt already evicted bare — it has no PDB, and --force allowed it. It's gone for good; nothing recreated it. The web Pods were recreated on the other nodes.
Careful: Never fix a blocked drain by force-deleting Pods or deleting the PDB in a hurry. Read ALLOWED DISRUPTIONS, then fix the budget or add replicas.
Checkpoint
node/lab-worker drained, and all 9 web Pods run on lab-worker2 and lab-worker3.

Uncordon — and why Pods don't come back

Slides 11, 15, 40 · Quiz Q4~5 min

Goal: Finish the maintenance, uncordon the node, and rebalance the app on purpose.

Run from: module5-lab/
Maintenance done — uncordon
kubectl uncordon lab-worker
sleep 5
kubectl get pods -l app=web -o custom-columns=NODE:.spec.nodeName --no-headers | sort | uniq -c
kubectl get pod pinned -o wide
Expected output
node/lab-worker uncordoned
      5 lab-worker2
      4 lab-worker3
NAME     READY   STATUS    RESTARTS   AGE   IP            NODE         NOMINATED NODE   READINESS GATES
pinned   1/1     Running   0          2m    10.244.2.95   lab-worker   <none>           <none>
Rebalance by replacing the Pods
kubectl rollout restart deployment/web
kubectl rollout status deployment/web --timeout=120s
until [ "$(kubectl get pods -l app=web --no-headers | wc -l)" -eq 9 ]; do sleep 2; done
kubectl get pods -l app=web -o custom-columns=NODE:.spec.nodeName --no-headers | sort | uniq -c
Expected output
deployment.apps/web restarted
...
deployment "web" successfully rolled out
      3 lab-worker
      3 lab-worker2
      3 lab-worker3
What just happened
  • pinned was Pending since Step 4. The moment the taint was gone, the scheduler placed it — Pending Pods are retried automatically.
  • Uncordon only removes the taint. The scheduler decides where a Pod goes once, when the Pod is created. Running Pods never move by themselves (Quiz Q4).
  • New Pods — from a rollout, a scale-up or a crash — will use lab-worker again. rollout restart replaces every Pod, so they spread out evenly.
  • The Deployment spread its Pods across nodes because the scheduler prefers to keep replicas of the same app apart. For hard guarantees, teams add topologySpreadConstraints.
  • The full routine from slide 15: cordon → drain → maintain → uncordon. Never power off a node before the drain has finished.
Checkpoint
Roughly 3 / 3 / 3 web Pods per worker.

Slide 18~4 min

Goal: Retire lab-worker3 the right way: drain, delete the Node object, then remove the machine.

Run from: module5-lab/
Terminal

kubectl delete node lab-worker3

node "lab-worker3" deleted
lab-worker3

What just happened

A DaemonSet node agent

Slides 19–22, 41 · Quiz Q6~7 min

Goal: Run a small agent on every node, see why the control plane is skipped, and include it with a toleration.

Run from: module5-lab/
Creates: daemonset.yaml
cat > daemonset.yaml <<'EOF'
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-agent
  labels:
    app: node-agent
spec:
  selector:
    matchLabels:
      app: node-agent
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
  template:
    metadata:
      labels:
        app: node-agent
    spec:
      containers:
        - name: agent
          image: busybox:1.37
          command:
            - sh
            - -c
            - |
              trap 'echo "stopping on $NODE_NAME"; exit 0' TERM
              while true; do
                echo "$(date -u +%T) agent on $NODE_NAME (interval ${INTERVAL}s)"
                sleep "$INTERVAL" & wait $!
              done
          env:
            - name: NODE_NAME
              valueFrom:
                fieldRef:
                  fieldPath: spec.nodeName
            - name: INTERVAL
              value: "30"
          resources:
            requests:
              cpu: 10m
              memory: 16Mi
            limits:
              cpu: 50m
              memory: 32Mi
EOF
Terminal
kubectl apply -f daemonset.yaml
kubectl rollout status daemonset/node-agent --timeout=90s
kubectl get daemonset node-agent
kubectl get pods -l app=node-agent -o custom-columns=POD:.metadata.name,NODE:.spec.nodeName
kubectl logs daemonset/node-agent

metadata:
  name: node-agent
  labels:
    app: node-agent
spec:

podFailurePolicy: stop retrying bugs

Slides 42, 44 · Quiz Q7~4 min

Goal: Tell the Job which failures are worth retrying and which aren't.

Run from: module5-lab/
Creates: job-policy.yaml
cat > job-policy.yaml <<'EOF'
apiVersion: batch/v1
kind: Job
metadata:
  name: policy-job
spec:
  backoffLimit: 6
  podFailurePolicy:
    rules:
      - action: FailJob          # a bug in our code: retrying won't help
        onExitCodes:
          containerName: task
          operator: In
          values: [42]
      - action: Ignore           # node drained / Pod evicted: retry for free
        onPodConditions:
          - type: DisruptionTarget
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: task
          image: busybox:1.37
          command: ["sh", "-c", "echo 'invalid input file'; exit 42"]
EOF
Terminal
kubectl apply -f job-policy.yaml
kubectl wait --for=condition=Failed job/policy-job --timeout=60s
kubectl get pods -l job-name=policy-job

policy-job-q48sq   0/1     Error    0          3s

Failed: Container task for pod default/policy-job-q48sq failed with exit code 42 matching FailJob rule at index 0
What just happened
  • backoffLimit: 6 would normally mean up to 7 tries over several minutes. The policy stopped it after one Pod in 3 seconds (Quiz Q7).
  • Rule 1: exit code 42 is how our program says "bad input" — retrying can't fix that, so FailJob.
  • Rule 2: a DisruptionTarget condition means the Pod was evicted — for example by a node drain. That's not the task's fault, so Ignore: retry without counting it against the backoff limit.
  • Agree on exit codes with your developers. It turns a vague "it failed 7 times" into a precise, fast signal.

A production-ready CronJob

Goal: Schedule a report every minute with the settings real teams use, trigger it by hand, and pause it.

Run from: module5-lab/
Creates: cronjob.yaml

apiVersion: batch/v1
kind: CronJob
metadata:
  name: report
spec:
  schedule: "*/1 * * * *"          # every minute (training only)
  timeZone: "Etc/UTC"
  concurrencyPolicy: Forbid         # never run two reports at once

EOF

  • Utilization is a percentage of the request. No request → nothing to divide by → <unknown>, and the HPA never scales.
  • kubectl autoscale … --cpu=50% is the quick imperative form. In Git, keep the autoscaling/v2 YAML.
  • The HPA adds Pods, not nodes. When new Pods stay Pending because the nodes are full, a node autoscaler — Cluster Autoscaler or Karpenter — adds nodes (slide 47). kind can't create machines, so we only discuss it.
Checkpoint
hpa-web went to 5 replicas under load and back to 1, and noreq showed <unknown>.

  • Four Pods on three nodes: one node briefly runs the old and the new agent side by side. With maxUnavailable: 0, no node is ever without its agent.

Troubleshooting

kubeadm join hangs with could not find a JWS signature in the cluster-info ConfigMap for token ID
The token is wrong or expired. Print a fresh command: docker exec lab-control-plane kubeadm token create --print-join-command (Step 2).
lab-worker3 never becomes Ready, or join waits 4 minutes for a healthy kubelet
Check the kubelet on the new node: docker exec lab-worker3 journalctl -u kubelet --no-pager | tail. Make sure you used --cgroupns=private and the same image as the other nodes. Remove it with docker rm -f -v lab-worker3 and kubectl delete node lab-worker3, then retry Step 3.
Pods on lab-worker3 stay in ImagePullBackOff
The new node pulls images itself. If your network blocks Docker Hub, copy them in with the pre-load commands at the top of this page.
docker run fails with network kind not found
Your cluster uses kind's default Docker network, called kind. Check with docker network ls. If it was created differently, use that network name.
kubectl drain keeps printing Cannot evict pod as it would violate the pod's disruption budget
A PodDisruptionBudget allows 0 disruptions. Check kubectl get pdb -A, then relax the budget or add replicas (Step 6). Press Ctrl+C to stop the drain.
A node stays Ready,SchedulingDisabled
It was cordoned (or drained) and never uncordoned: kubectl uncordon <node>.
DaemonSet DESIRED is lower than the number of nodes
Some nodes have taints the Pod doesn't tolerate (the control plane), or don't match its nodeSelector. Compare kubectl describe node with the DaemonSet spec (Steps 9–10).
A Job never finishes and its Pod shows CrashLoopBackOff
The Pod uses restartPolicy: OnFailure. Read kubectl logs job/<name>; the Job fails when backoffLimit is reached.
A CronJob runs at the wrong hour
Set spec.timeZone (for example Europe/Berlin). Without it, the controller's time zone — usually UTC — is used.
kind load fails with ctr: content digest sha256:… not found
Docker 29 keeps images in its containerd image store: it downloads only your platform, but docker save still lists all of them, and kind's import looks for every one. Save just your platform and load the archive — that's what the pre-load commands at the top of this page do: docker save --platform "$(docker version --format '{{.Server.Os}}/{{.Server.Arch}}')" -o image.tar IMAGE then kind load image-archive image.tar --name lab. Images you built yourself (like module1-demo-api) load fine with kind load docker-image.
ERROR: unknown containerd config version: 4 from kind
Your kind binary is older than the node image. Install kind v0.33 or newer (Module 2, Step 1) and run kind version to check.
