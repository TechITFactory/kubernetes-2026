Create ConfigMaps three ways

Slides 3–6~6 min

Goal: Create one ConfigMap from YAML and one from a file, then look at what Kubernetes stored.

Run from: module6-lab/
Creates: configmap.yaml
cat > configmap.yaml <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: my-config
data:
  APP_MODE: "production"
  APP_VERSION: "v1.0"
EOF
Declarative — the way to go for anything you keep
kubectl apply -f configmap.yaml
kubectl describe configmap my-config | sed -n '/^Data/,/^BinaryData/p'
Expected output
configmap/my-config created
Data
====
APP_MODE:
----
production

APP_VERSION:
----
v1.0


BinaryData
From a file — generate the YAML, then apply it
printf 'APP_MODE=production\nAPP_VERSION=v1.0\n' > app.properties
kubectl create configmap config-volume --from-file=app.properties \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl get configmap config-volume -o jsonpath='{.data}'; echo
kubectl get configmaps
Expected output
configmap/config-volume created
{"app.properties":"APP_MODE=production\nAPP_VERSION=v1.0\n"}
NAME               DATA   AGE
config-volume      1      0s
kube-root-ca.crt   1      4h
my-config          2      5s
What just happened
  • A ConfigMap is a small key–value store for non-secret settings: URLs, feature flags, log levels, whole config files.
  • describe prints the values in clear text. That's fine for a ConfigMap — and the reason passwords never go in one.
  • --from-file makes the file name the key and the file content the value. Handy for nginx.conf, app.properties and friends.
  • create … --dry-run=client -o yaml | kubectl apply -f - is a common idiom: generate YAML from a file, then apply it. Run it again after editing the file and it updates the ConfigMap.
  • The quick imperative way also exists — kubectl create configmap my-config --from-literal=APP_MODE=production — great for experiments, but it leaves nothing to review in Git.
Checkpoint
Three ConfigMaps: config-volume (1 key), kube-root-ca.crt, my-config (2 keys).

Consume a ConfigMap: env, volume and subPath

Slides 7–8, 34~6 min

Goal: Give one Pod the same data three ways and see how each one looks inside the container.

Run from: module6-lab/
Creates: cm-pod.yaml
cat > cm-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: cm-pod
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]
      envFrom:
        - configMapRef:
            name: my-config
      volumeMounts:
        - name: config
          mountPath: /etc/config
        - name: config
          mountPath: /etc/app.properties
          subPath: app.properties
  volumes:
    - name: config
      configMap:
        name: config-volume
EOF
Terminal
kubectl apply -f cm-pod.yaml
kubectl wait --for=condition=Ready pod/cm-pod --timeout=60s
kubectl exec cm-pod -- sh -c 'echo "env:     APP_MODE=$APP_MODE"; echo "volume:"; ls -l /etc/config; echo "subPath:"; ls -l /etc/app.properties'
Expected output
pod/cm-pod created
pod/cm-pod condition met
env:     APP_MODE=production
volume:
total 0
lrwxrwxrwx    1 root     root            21 Sep 29 06:44 app.properties -> ..data/app.properties
subPath:
-rw-r--r--    1 root     root            37 Sep 29 06:44 /etc/app.properties
What just happened
  • envFrom turns every key of my-config into an environment variable.
  • A volume turns every key of config-volume into a file. Look closely: it's a symlink into a hidden ..data folder. The kubelet updates it by swapping that folder in one step.
  • subPath mounts a single file at an exact path — useful when the folder already has other files (like /etc/nginx). But it's a plain copy, not a symlink. Remember that for the next step.
Checkpoint
The env var says production, the volume file is a symlink, and the subPath file is a regular file.

Change the ConfigMap — who notices?

Slides 9, 34 · Quiz Q1, Q2~6 min

Goal: Update both ConfigMaps while the Pod runs, and find out which of the three views changes.

Run from: module6-lab/
Update the file-based and the env-based ConfigMap
printf 'APP_MODE=development\nAPP_VERSION=v2.0\n' > app.properties
kubectl create configmap config-volume --from-file=app.properties \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl patch configmap my-config -p '{"data":{"APP_MODE":"development"}}'
Expected output
configmap/config-volume configured
configmap/my-config patched
Wait for the kubelet, then compare (can take up to ~2 minutes)
start=$(date +%s)
until kubectl exec cm-pod -- grep -q development /etc/config/app.properties 2>/dev/null; do sleep 3; done
echo "volume updated after $(( $(date +%s) - start ))s"
kubectl exec cm-pod -- sh -c 'echo "env:     APP_MODE=$APP_MODE"; echo "volume:  $(head -1 /etc/config/app.properties)"; echo "subPath: $(head -1 /etc/app.properties)"'
Expected output
volume updated after 64s
env:     APP_MODE=production
volume:  APP_MODE=development
subPath: APP_MODE=production
What just happened
  • Volume: updated in place. The kubelet refreshes ConfigMap volumes on its sync loop — anything from a few seconds to a minute or two. Apps that re-read their file (or watch it) pick up changes without a restart.
  • Env var: still production. Environment variables are set once, when the container starts (Quiz Q1).
  • subPath: still production. A subPath mount is a copy made at start-up and never updates (Quiz Q2).
  • The fix for both is a restart. For a Deployment: kubectl rollout restart deployment/<name> — a normal rolling update with no downtime.
Checkpoint
Only the volume line says development.

Missing, optional and immutable ConfigMaps

Slides 10, 35, 41 · Quiz Q3~6 min

Goal: See the two errors a missing ConfigMap causes, the optional escape hatch, and a ConfigMap that can't be changed.

Run from: module6-lab/
Delete the ConfigMap that env vars need
kubectl delete pod cm-pod --now
kubectl delete configmap my-config
Expected output
pod "cm-pod" deleted from default namespace
configmap "my-config" deleted from default namespace
Creates: three Pods that reference missing ConfigMaps
cat > needs-config.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: needs-config
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]
      envFrom:
        - configMapRef:
            name: my-config          # we delete it first
EOF
cat > needs-volume.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: needs-volume
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]
      volumeMounts:
        - name: config
          mountPath: /etc/config
  volumes:
    - name: config
      configMap:
        name: nope                   # does not exist
EOF
cat > optional-config.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: optional-config
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]
      envFrom:
        - configMapRef:
            name: my-config
            optional: true           # start even if it is missing
EOF
Terminal
kubectl apply -f needs-config.yaml -f needs-volume.yaml -f optional-config.yaml
sleep 10
kubectl get pods needs-config needs-volume optional-config
kubectl get events --field-selector involvedObject.name=needs-config,reason=Failed -o custom-columns=MESSAGE:.message | tail -1
kubectl get events --field-selector involvedObject.name=needs-volume,reason=FailedMount -o custom-columns=MESSAGE:.message | tail -1
Expected output
pod/needs-config created
pod/needs-volume created
pod/optional-config created
NAME              READY   STATUS                       RESTARTS   AGE
needs-config      0/1     CreateContainerConfigError   0          10s
needs-volume      0/1     ContainerCreating            0          10s
optional-config   1/1     Running                      0          10s
MESSAGE
Error: configmap "my-config" not found
MESSAGE
MountVolume.SetUp failed for volume "config" : configmap "nope" not found
Creates: app-config-v1.yaml — an immutable ConfigMap
cat > app-config-v1.yaml <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config-v1
immutable: true
data:
  APP_MODE: production
EOF
kubectl apply -f app-config-v1.yaml
kubectl patch configmap app-config-v1 -p '{"data":{"APP_MODE":"debug"}}'
Expected output
configmap/app-config-v1 created
The ConfigMap "app-config-v1" is invalid: data: Forbidden: field is immutable when `immutable` is set
Tidy up
kubectl delete pod needs-config needs-volume optional-config --now
kubectl delete configmap app-config-v1
Expected output
pod "needs-config" deleted from default namespace
pod "needs-volume" deleted from default namespace
pod "optional-config" deleted from default namespace
configmap "app-config-v1" deleted from default namespace
What just happened
  • Missing ConfigMap for env → CreateContainerConfigError. Missing ConfigMap for a volume → stuck in ContainerCreating with a FailedMount event. Both fix themselves as soon as the ConfigMap exists (Quiz Q3).
  • optional: true lets the Pod start anyway — only for settings the app can really live without.
  • immutable: true (stable since v1.21) blocks edits. To change config you create app-config-v2 and point the Deployment at it — a normal rollout you can roll back. It also saves the kubelet from watching the object.
  • Pods that were already running keep what they had when a ConfigMap is deleted. Only new Pods fail.
Checkpoint
needs-config and needs-volume were stuck, optional-config ran, and the immutable ConfigMap refused the patch.

Secrets: base64 is not encryption

Slides 11–13, 17, 36 · Quiz Q4, Q5~8 min

Goal: Create a Secret two ways, decode it in one command, and catch a real leak in kubectl apply.

Run from: module6-lab/
Imperative — and decode it
kubectl create secret generic my-secret \
  --from-literal=DB_USER=admin --from-literal=DB_PASSWORD=SuperSecret123
kubectl get secret my-secret
kubectl describe secret my-secret | sed -n '/^Data/,$p'
kubectl get secret my-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d; echo
kubectl delete secret my-secret
Expected output
secret/my-secret created
NAME        TYPE     DATA   AGE
my-secret   Opaque   2      0s
Data
====
DB_PASSWORD:  14 bytes
DB_USER:      5 bytes
SuperSecret123
secret "my-secret" deleted from default namespace
Creates: secret.yaml — stringData lets you write clear text
cat > secret.yaml <<'EOF'
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
stringData:
  DB_USER: app_user
  DB_PASSWORD: "S3cure-Pa55w0rd!"
EOF
Client-side apply — look at the annotations
kubectl apply -f secret.yaml
kubectl get secret db-credentials -o jsonpath='{.metadata.annotations}'; echo
Expected output
secret/db-credentials created
{"kubectl.kubernetes.io/last-applied-configuration":"{\"apiVersion\":\"v1\",\"kind\":\"Secret\",\"metadata\":{\"annotations\":{},\"name\":\"db-credentials\",\"namespace\":\"default\"},\"stringData\":{\"DB_PASSWORD\":\"S3cure-Pa55w0rd!\",\"DB_USER\":\"app_user\"},\"type\":\"Opaque\"}\n"}
Server-side apply — the fix
kubectl delete secret db-credentials
kubectl apply --server-side -f secret.yaml
kubectl get secret db-credentials -o jsonpath='{.metadata.annotations}'; echo "(no annotations)"
Expected output
secret "db-credentials" deleted from default namespace
secret/db-credentials serverside-applied
(no annotations)
What just happened
  • describe shows only byte counts. But anyone who can get the Secret can decode it with base64 -d. Base64 is encoding, not encryption (Quiz Q4).
  • stringData is a write-only convenience: you write clear text, Kubernetes stores it base64-encoded under data.
  • The leak: a normal (client-side) kubectl apply saves the whole file in the last-applied-configuration annotation — including your password in clear text. Anyone who can read Secret metadata can see it.
  • kubectl apply --server-side tracks ownership on the server and writes no such annotation. Use it — or kubectl create secret — for every Secret (Quiz Q5).
  • In real teams the value comes from a secret manager (External Secrets Operator, Secrets Store CSI driver). Real Secret YAML never goes into Git.
Checkpoint
You decoded SuperSecret123, saw S3cure-Pa55w0rd! in an annotation, and the server-side apply left no annotations.

Mount a Secret the safe way

Slides 14–15, 37~5 min

Goal: Use one key as an env var and mount the Secret as read-only files with tight permissions.

Run from: module6-lab/
Creates: secret-pod.yaml
cat > secret-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: secret-pod
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 1000
    fsGroup: 1000
  containers:
    - name: app
      image: busybox:1.37
      command: ["sleep", "3600"]
      env:
        - name: DB_USER
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: DB_USER
      volumeMounts:
        - name: creds
          mountPath: /etc/db
          readOnly: true
  volumes:
    - name: creds
      secret:
        secretName: db-credentials
        defaultMode: 0440
EOF
Terminal
kubectl apply -f secret-pod.yaml
kubectl wait --for=condition=Ready pod/secret-pod --timeout=60s
kubectl exec secret-pod -- sh -c 'id; echo DB_USER=$DB_USER; ls -lL /etc/db; mount | grep /etc/db'
Expected output
pod/secret-pod created
pod/secret-pod condition met
uid=1000 gid=1000 groups=1000
DB_USER=app_user
total 8
-r--r-----    1 root     1000            16 Sep 29 06:45 DB_PASSWORD
-r--r-----    1 root     1000             8 Sep 29 06:45 DB_USER
tmpfs on /etc/db type tmpfs (ro,relatime,size=16481980k,noswap)
What just happened
  • securityContext (the runAsUser and fsGroup lines in the file) is used here only so the app can read the Secret files. It is taught properly in Module 7, slides 11–13.
  • secretKeyRef picks one key into one env var. Prefer files for passwords: env vars show up in crash dumps, /proc and careless debug logs.
  • defaultMode: 0440 + fsGroup: 1000: the files are readable by the app's group only. Kubernetes' default (0644) is readable by every user in the container.
  • The mount is tmpfs — the Secret lives in the node's memory and is never written to its disk.
  • readOnly: true means the app can't change or delete its credentials by mistake.
Checkpoint
Permissions -r--r-----, group 1000, and a tmpfs mount.
8

Rotate a Secret

Slides 16, 37~4 min

Goal: Change the password and see which view of the Secret follows.

Run from: module6-lab/
Takes up to ~2 minutes
kubectl patch secret db-credentials -p '{"stringData":{"DB_PASSWORD":"Rotated-2026!"}}'
start=$(date +%s)
until kubectl exec secret-pod -- grep -q Rotated /etc/db/DB_PASSWORD 2>/dev/null; do sleep 5; done
echo "file updated after $(( $(date +%s) - start ))s"
kubectl exec secret-pod -- cat /etc/db/DB_PASSWORD; echo
Expected output
secret/db-credentials patched
file updated after 5s
Rotated-2026!
What just happened
  • The mounted file changed without a restart. Secrets use the same kubelet sync as ConfigMaps — from a few seconds up to a minute or two, depending on where the sync loop happens to be. Your Step 4 and Step 8 times will differ.
  • An app that re-reads the file on every new connection picks up the new password automatically. Env vars ($DB_USER here) would need a Pod restart.
  • Real rotation needs overlap: the database must accept the old and the new password for a while, or connections fail during the switch.
Checkpoint
The file shows Rotated-2026!.

An init container that waits for a dependency

Slides 18–20, 38 · Quiz Q6~5 min

Goal: Hold an app back until its database Service exists — instead of letting it crash-loop.

Run from: module6-lab/
Creates: wait-for-db.yaml
cat > wait-for-db.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: orders-app
spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.37
      command: ["sh", "-c", "until nslookup orders-db.default.svc.cluster.local >/dev/null 2>&1; do echo waiting for orders-db; sleep 2; done; echo orders-db is resolvable"]
  containers:
    - name: app
      image: nginx:1.28-alpine
EOF
No database yet
kubectl apply -f wait-for-db.yaml
sleep 8
kubectl get pod orders-app
kubectl logs orders-app -c wait-for-db --tail=2
Expected output
pod/orders-app created
NAME         READY   STATUS     RESTARTS   AGE
orders-app   0/1     Init:0/1   0          8s
waiting for orders-db
waiting for orders-db
Create the Service — the app starts by itself
kubectl create service clusterip orders-db --tcp=5432:5432
kubectl wait --for=condition=Ready pod/orders-app --timeout=60s
kubectl get pod orders-app
kubectl logs orders-app -c wait-for-db --tail=1
Expected output
service/orders-db created
pod/orders-app condition met
NAME         READY   STATUS    RESTARTS   AGE
orders-app   1/1     Running   0          12s
orders-db is resolvable
What just happened
  • Init:0/1 means "0 of 1 init containers finished". The app container hasn't even been created yet (Quiz Q6).
  • The init container polls DNS every 2 seconds. As soon as the Service exists, it exits with 0 and the app starts.
  • Without it, the app would start, fail to connect, crash, and back off — CrashLoopBackOff for a problem that isn't the app's fault.
  • Keep waits like this short and simple. The app should still retry its own connections — the database can go away later, too.
Checkpoint
The Pod went from Init:0/1 to Running right after the Service appeared.

A failing init container

Slides 21–22, 38~4 min

Goal: See how a failing init container blocks the app, and how to read its logs.

Run from: module6-lab/
Creates: failing-init.yaml
cat > failing-init.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: failing-init
spec:
  initContainers:
    - name: migrate
      image: busybox:1.37
      command: ["sh", "-c", "echo 'running migrations...'; echo 'ERROR: relation users already exists'; exit 1"]
  containers:
    - name: app
      image: nginx:1.28-alpine
EOF
Wait ~25 s for a few retries
kubectl apply -f failing-init.yaml
sleep 25
kubectl get pod failing-init
kubectl logs failing-init -c migrate
kubectl logs failing-init
Expected output
pod/failing-init created
NAME           READY   STATUS                  RESTARTS      AGE
failing-init   0/1     Init:Error   2 (23s ago)   25s
running migrations...
ERROR: relation users already exists
Defaulted container "app" out of: app, migrate (init)
Error from server (BadRequest): container "app" in pod "failing-init" is waiting to start: PodInitializing
What just happened
  • The kubelet retries the init container with growing back-off: Init:Error, then Init:CrashLoopBackOff. The app container never starts.
  • kubectl logs <pod> picks the app container, which has no logs. Name the init container with -c migrate to see the real error.
  • Running database migrations in an init container is common — but every replica runs it. Make migrations safe to run twice, or run them once in a Job instead.
Checkpoint
Init:Error (or Init:CrashLoopBackOff, between retries) and the ERROR: relation users already exists log line.

An init container renders a config file

Slides 23, 38~5 min

Goal: Combine a ConfigMap template and a Secret into one ready-to-use config file before the app starts.

Run from: module6-lab/
Creates: render-config.yaml
cat > render-config.yaml <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: db-template
data:
  db.conf.tpl: |
    host=orders-db.default.svc.cluster.local
    port=5432
    user=__DB_USER__
    password=__DB_PASSWORD__
---
apiVersion: v1
kind: Pod
metadata:
  name: render-config
spec:
  volumes:
    - name: templates
      configMap:
        name: db-template
    - name: config
      emptyDir:
        medium: Memory                 # rendered secrets stay in RAM
  initContainers:
    - name: render
      image: busybox:1.37
      command:
        - sh
        - -c
        - |
          sed -e "s/__DB_USER__/$DB_USER/" -e "s/__DB_PASSWORD__/$DB_PASSWORD/" \
              /templates/db.conf.tpl > /config/db.conf
          chmod 0400 /config/db.conf
          echo "rendered /config/db.conf"
      env:
        - name: DB_USER
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: DB_USER
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: DB_PASSWORD
      volumeMounts:
        - name: templates
          mountPath: /templates
        - name: config
          mountPath: /config
  containers:
    - name: app
      image: busybox:1.37
      command: ["sh", "-c", "grep -v password /config/db.conf; sleep 3600"]
      volumeMounts:
        - name: config
          mountPath: /config
          readOnly: true
EOF
Terminal
kubectl apply -f render-config.yaml
kubectl wait --for=condition=Ready pod/render-config --timeout=60s
kubectl logs render-config -c render
kubectl logs render-config -c app
kubectl exec render-config -c app -- ls -l /config/db.conf
Expected output
configmap/db-template created
pod/render-config created
pod/render-config condition met
rendered /config/db.conf

  • Init writes → shared emptyDir → app reads. The app gets one finished file and needs no templating logic of its own.

  • The Secret is consumed only by the init container. The app container never sees it as an env var.

Sidecar: ship the app's logs

Slides 24–26~4 min

Goal: Run nginx with a helper container that follows its access log.

Run from: module6-lab/
Creates: sidecar-pod.yaml
cat > sidecar-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: sidecar-pod
spec:
  volumes:
    - name: logs
      emptyDir: {}
  containers:
    - name: web
      image: nginx:1.28-alpine
      volumeMounts:
        - name: logs
          mountPath: /var/log/nginx
    - name: log-shipper
      image: busybox:1.37
      command: ["sh", "-c", "trap 'exit 0' TERM; touch /var/log/nginx/access.log; tail -F /var/log/nginx/access.log & wait"]
      volumeMounts:
        - name: logs
          mountPath: /var/log/nginx
EOF

What just happened
  • Both containers mount the same emptyDir at /var/log/nginx. nginx writes, the sidecar reads.
  • The request came from 127.0.0.1: containers in one Pod share one network, so localhost is the same for both.
  • With more than one container, kubectl logs and exec need -c to pick one.
  • The trap … TERM line lets the sidecar stop instantly when the Pod is deleted, instead of waiting 30 seconds.

Adapter: turn plain text into JSON

Slides 27–28 · Quiz Q9~4 min

Goal: Let a helper translate a legacy app's log format into what your logging system expects.

Run from: module6-lab/
Creates: adapter-pod.yaml
cat > adapter-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: adapter-pod
spec:
  volumes:
    - name: logs
      emptyDir: {}
  containers:
    - name: app                        # legacy app: plain-text log lines
      image: busybox:1.37
      command:
        - sh
        - -c
        - |
          trap 'exit 0' TERM
          while true; do
            echo "$(date -u +%T) error: payment failed order=$RANDOM" >> /logs/app.log
            sleep 3 & wait $!
          done
      volumeMounts:
        - name: logs
          mountPath: /logs
    - name: json-adapter               # turns each line into JSON on stdout
      image: busybox:1.37
      command:
        - sh
        - -c
        - |
          trap 'exit 0' TERM
          touch /logs/app.log
          tail -F /logs/app.log | while read t level msg; do
            echo "{\"time\":\"$t\",\"level\":\"${level%:}\",\"msg\":\"$msg\"}"
          done &
          wait
      volumeMounts:
        - name: logs
          mountPath: /logs
EOF
Terminal
kubectl apply -f adapter-pod.yaml
kubectl wait --for=condition=Ready pod/adapter-pod --timeout=60s
sleep 7
kubectl exec adapter-pod -c app -- tail -2 /logs/app.log
kubectl logs adapter-pod -c json-adapter --tail=2
Expected output
pod/adapter-pod created
pod/adapter-pod condition met
06:49:48 error: payment failed order=6841
06:49:51 error: payment failed order=18591
{"time":"06:49:48","level":"error","msg":"payment failed order=6841"}
{"time":"06:49:51","level":"error","msg":"payment failed order=18591"}
What just happened
  • An adapter changes the shape of what the app produces — here plain text into JSON on stdout, where the cluster's log collector picks it up (Quiz Q9).
  • The legacy app didn't change at all. That's the point: fix the format next to the app, not inside it.
  • Real-world adapters: log reformatters, metrics exporters that turn an app's stats page into Prometheus metrics.
Checkpoint
The same two events, once as plain text and once as JSON.

Ambassador: a local proxy — and startup order

Goal: Let the app call localhost:8080 while an nginx ambassador talks to the real backend. Then fix a start-up race with a native sidecar.

Run from: module6-lab/
Creates: orders-api.yaml — the backend
cat > orders-api.yaml <<'EOF'
apiVersion: v1

  name: orders-api-content

  index.html: |
    {"service":"orders-api","orders":42}

  name: orders-api

  replicas: 2

    matchLabels:
      app: orders-api

---

  name: orders-api

  selector:
    app: orders-api

Creates: ambassador-pod.yaml — proxy config + Pod
cat > ambassador-pod.yaml <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: ambassador-config
data:
  default.conf: |
    server {
      listen 8080;
      location / {
        proxy_pass http://orders-api.default.svc.cluster.local;
        proxy_connect_timeout 2s;
        proxy_read_timeout 5s;
        add_header X-Via ambassador;
      }
    }
---
apiVersion: v1
kind: Pod
metadata:
  name: ambassador-pod
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sh", "-c", "while true; do wget -qO- http://localhost:8080; sleep 5; done"]
    - name: ambassador
      image: nginx:1.28-alpine
      ports:
        - containerPort: 8080
      volumeMounts:
        - name: config
          mountPath: /etc/nginx/conf.d
  volumes:
    - name: config
      configMap:
        name: ambassador-config
EOF

Creates: ambassador-native.yaml — the same proxy as a native sidecar
cat > ambassador-native.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: ambassador-native
spec:
  initContainers:
    - name: ambassador
      image: nginx:1.28-alpine
      restartPolicy: Always              # native sidecar
      ports:
        - containerPort: 8080
      startupProbe:                      # app starts only after this passes
        tcpSocket:
          port: 8080
        periodSeconds: 1
        failureThreshold: 30
      volumeMounts:
        - name: config
          mountPath: /etc/nginx/conf.d
  containers:
    - name: app
      image: busybox:1.37
      command: ["sh", "-c", "while true; do wget -qO- http://localhost:8080; echo; sleep 5; done"]
  volumes:
    - name: config
      configMap:
        name: ambassador-config
EOF
Terminal
kubectl apply -f ambassador-native.yaml
kubectl wait --for=condition=Ready pod/ambassador-native --timeout=60s
sleep 2
kubectl logs ambassador-native -c app | head -1
Expected output
pod/ambassador-native created
pod/ambassador-native condition met
{"service":"orders-api","orders":42}
What just happened
  • The app only knows localhost:8080. The ambassador owns the real address, timeouts and headers — change them in the ConfigMap, not in the app.
  • In the classic version the first request failed: both containers start at the same time, and the app was faster than nginx. You may or may not hit this race on your machine — in production you will, eventually.
  • In the native version the ambassador is an initContainer with restartPolicy: Always and a startupProbe. Kubernetes starts it first and waits until port 8080 answers before starting the app (Quiz Q8).
  • This also combines Parts A and D: a ConfigMap delivers the nginx config file into the sidecar.
Checkpoint
The classic Pod may log a Connection refused first; the native one answers correctly from the first request.

Troubleshooting

Pod stuck in CreateContainerConfigError
A ConfigMap or Secret used for env vars doesn't exist, or a key is missing. Read kubectl describe pod → Events, then create it (Step 5).
Pod stuck in ContainerCreating with FailedMount
A ConfigMap or Secret used as a volume doesn't exist. Create it, or set optional: true if the app can run without it (Step 5).
The mounted file doesn't change after kubectl apply
Wait up to 2 minutes for the kubelet sync. If it's mounted with subPath, it never updates — restart the Pod (Step 4).
error: … is invalid: data: Forbidden: field is immutable
The ConfigMap or Secret has immutable: true. Create a new one with a new name and point the Pod or Deployment at it.
base64: invalid input when decoding
Use -o jsonpath='{.data.KEY}' for exactly one value. On macOS, use base64 -D if -d isn't accepted.
Pod stuck in Init:0/1
An init container hasn't finished. Read its logs: kubectl logs <pod> -c <init-container> (Steps 9–10).
kubectl logs says Defaulted container … or shows the wrong output
The Pod has several containers. Add -c <name>. List them with kubectl get pod <pod> -o jsonpath='{.spec.containers[*].name}'.
A Pod takes 30 seconds to delete
A shell script running as PID 1 ignores SIGTERM. Add trap 'exit 0' TERM (as in the lab files), or use kubectl delete … --now in labs.
A Job with a sidecar never completes
The sidecar is in containers. Move it to initContainers with restartPolicy: Always (Step 15).
kind load fails with ctr: content digest sha256:… not found
Docker 29 keeps images in its containerd image store: it downloads only your platform, but docker save still lists all of them, and kind's import looks for every one. Save just your platform and load the archive — that's what the pre-load commands at the top of this page do: docker save --platform "$(docker version --format '{{.Server.Os}}/{{.Server.Arch}}')" -o image.tar IMAGE then kind load image-archive image.tar --name lab. Images you built yourself (like module1-demo-api) load fine with kind load docker-image.
ERROR: unknown containerd config version: 4 from kind
Your kind binary is older than the node image. Install kind v0.33 or newer (Module 2, Step 1) and run kind version to check.
