What just happened
  • A Namespace is a folder for objects. Pods, Services and Deployments live in a namespace; Nodes and Namespaces themselves are cluster-wide (NAMESPACED false).

  • Kubernetes adds the kubernetes.io/metadata.name label to every namespace, so policies can select namespaces by name.
  • Switching the context namespace is handy, but easy to forget. Always switch back — later steps expect default.

ResourceQuota: watch the API server say no

M4 slides 6–8, 31 · Quiz Q2~7 min

Goal: Put a budget on testns, then try two Pods that break it: one with no resource numbers, one that asks for too much memory.

Run from: module4-lab/
Creates: resourcequota.yaml
cat > resourcequota.yaml <<'EOF'
apiVersion: v1
kind: ResourceQuota
metadata:
  name: testnsquota
  namespace: testns
spec:
  hard:
    pods: "2"
    requests.cpu: "1"
    requests.memory: 1Gi
    limits.cpu: "2"
    limits.memory: 2Gi
EOF
Terminal
kubectl apply -f resourcequota.yaml
kubectl get resourcequota -n testns
Expected output
resourcequota/testnsquota created
NAME          REQUEST                                                LIMIT                                   AGE
testnsquota   pods: 0/2, requests.cpu: 0/1, requests.memory: 0/1Gi   limits.cpu: 0/2, limits.memory: 0/2Gi   0s
A Pod with no requests or limits
kubectl run nores -n testns --image=nginx:1.28-alpine
Expected output
Error from server (Forbidden): pods "nores" is forbidden: failed quota: testnsquota: must specify limits.cpu for: nores; limits.memory for: nores; requests.cpu for: nores; requests.memory for: nores
Creates: highmem-pod.yaml — asks for 2Gi of memory
cat > highmem-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: highmem-pod
  namespace: testns
spec:
  containers:
    - name: app
      image: nginx:1.28-alpine
      resources:
        requests:
          cpu: 100m
          memory: 2Gi
        limits:
          cpu: 200m
          memory: 2Gi
EOF
Terminal
kubectl apply -f highmem-pod.yaml
Expected output
Error from server (Forbidden): error when creating "highmem-pod.yaml": pods "highmem-pod" is forbidden: exceeded quota: testnsquota, requested: requests.memory=2Gi, used: requests.memory=0, limited: requests.memory=1Gi
What just happened
  • A ResourceQuota is checked at admission — before anything is saved. Rejected Pods never exist, so there's nothing to describe; the error message is all you get.
  • Once a quota tracks CPU or memory, every new Pod must say how much it needs. Otherwise the quota can't count it, so the API server refuses it.
  • The second error is plain arithmetic: 2Gi requested + 0 used > 1Gi allowed.
Checkpoint
Both Pods were Forbidden, and kubectl get pods -n testns shows nothing.

LimitRange defaults — and a Deployment stuck by quota

M4 slides 8, 31, 39 · Quiz Q1~8 min

Goal: Give testns sensible defaults, fill the Pod quota, and see how a Deployment fails quietly when the quota is full.

Run from: module4-lab/
Creates: limitrange.yaml
cat > limitrange.yaml <<'EOF'
apiVersion: v1
kind: LimitRange
metadata:
  name: defaults
  namespace: testns
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 100m
        memory: 64Mi
      default:
        cpu: 200m
        memory: 128Mi
EOF
Terminal
kubectl apply -f limitrange.yaml
kubectl run web1 -n testns --image=nginx:1.28-alpine
kubectl run web2 -n testns --image=nginx:1.28-alpine
kubectl get pod web1 -n testns -o jsonpath='{.spec.containers[0].resources}'; echo
Expected output
limitrange/defaults created
pod/web1 created
pod/web2 created
{"limits":{"cpu":"200m","memory":"128Mi"},"requests":{"cpu":"100m","memory":"64Mi"}}
The third Pod is one too many
kubectl run web3 -n testns --image=nginx:1.28-alpine
kubectl describe resourcequota testnsquota -n testns
Expected output
Error from server (Forbidden): pods "web3" is forbidden: exceeded quota: testnsquota, requested: pods=1, used: pods=2, limited: pods=2
Name:            testnsquota
Namespace:       testns
Resource         Used   Hard
--------         ----   ----
limits.cpu       400m   2
limits.memory    256Mi  2Gi
pods             2      2
requests.cpu     200m   1
requests.memory  128Mi  1Gi
Now a Deployment
kubectl create deployment qdemo -n testns --image=nginx:1.28-alpine --replicas=2
sleep 3
kubectl get deploy qdemo -n testns
kubectl get deploy qdemo -n testns -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'
kubectl get events -n testns --field-selector reason=FailedCreate -o custom-columns=MESSAGE:.message | head -2
Expected output
deployment.apps/qdemo created
NAME    READY   UP-TO-DATE   AVAILABLE   AGE
qdemo   0/2     0            0           3s
Progressing=True NewReplicaSetCreated
Available=False MinimumReplicasUnavailable
ReplicaFailure=True FailedCreate
MESSAGE
Error creating: pods "qdemo-697d44df9-t22j6" is forbidden: exceeded quota: testnsquota, requested: pods=1, used: pods=2, limited: pods=2
Delete the namespace — and everything in it
kubectl delete namespace testns
Expected output
namespace "testns" deleted
What just happened
  • The LimitRange filled in requests and limits for Pods that didn't set any. That's why web1 was accepted this time.
  • The Deployment said created — no error! The ReplicaSet tries to create Pods, and it gets rejected. You only see that in the Deployment's conditions (ReplicaFailure) and in events (Quiz Q1).
  • Production habit: when READY stays at 0, check kubectl describe deploy and events before you look at logs. There are no Pods to log yet.
  • Deleting a Namespace deletes every object inside it: Pods, the Deployment, the quota and the LimitRange. Handy for cleanup, dangerous in production.
Checkpoint
kubectl get namespace testns now says NotFound (it may show Terminating for a few seconds first).

Add, change and remove a label
kubectl label pod pod-d env=dev

What just happened
  • Comma means AND: app=web,tier!=backend needs both to be true.
  • Set-based selectors: in (a,b), notin (a,b), and !env ("has no env label"). Deployments and ReplicaSets accept these through matchExpressions.
  • -L tier,env adds label columns — faster to read than --show-labels.
  • Changing a label needs --overwrite. That safety net stops you from silently re-routing a Service by accident (Module 3, Step 10).
  • kubectl delete -l is powerful. Always run the same selector with get first.
Checkpoint

Annotations

M4 slides 12–13 · Quiz Q7~5 min

Goal: Attach metadata for tools and people, change it safely, and see that annotations can't be used to select objects.

Run from: module4-lab/
Terminal
kubectl run annotation-demo --image=nginx:1.28-alpine --annotations=build-version=1.2.3 --annotations=owner=dev-team
kubectl annotate pod annotation-demo description="demo pod for module 4"
kubectl get pod annotation-demo -o jsonpath='{.metadata.annotations}'; echo
Expected output
pod/annotation-demo created
pod/annotation-demo annotated
{"build-version":"1.2.3","description":"demo pod for module 4","owner":"dev-team"}
Change one, remove one, try to select by one
kubectl annotate pod annotation-demo owner=platform-team
kubectl annotate pod annotation-demo owner=platform-team --overwrite
kubectl annotate pod annotation-demo description-
kubectl get pod annotation-demo -o jsonpath='{.metadata.annotations}'; echo
kubectl get pods -l owner=platform-team

error: --overwrite is false but found the following declared annotation(s): 'owner' already has a value (dev-team)

kubectl delete pod annotation-demo --now

pod "annotation-demo" deleted from default namespace
What just happened
  • Annotations hold information: build numbers, Git commits, owners, links to dashboards, tool settings. Values can be long — up to 256 KB in total.
  • Labels are for selection. -l owner=… found nothing because owner is an annotation, not a label.
  • Rule of thumb: "Should Kubernetes pick this object by it?" → label. "Should a person or tool read it?" → annotation.
  • You'll use one annotation all the time: kubernetes.io/change-cause (Step 9).

A ReplicaSet heals itself

M4 slides 14–16, 33~6 min

Goal: Run 3 copies of nginx with a ReplicaSet, check who owns each Pod, then delete one and watch it come back.

Run from: module4-lab/
Creates: nginx-rs.yaml
cat > nginx-rs.yaml <<'EOF'
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: nginx-rs
  labels:
    app: nginx-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx-rs
  template:
    metadata:
      labels:
        app: nginx-rs
    spec:
      containers:
        - name: nginx
          image: nginx:1.28-alpine
          ports:
            - containerPort: 80
EOF
Terminal
kubectl apply -f nginx-rs.yaml
kubectl wait --for=condition=Ready pod -l app=nginx-rs --timeout=60s
kubectl get rs nginx-rs
kubectl get pods -l app=nginx-rs -o custom-columns=NAME:.metadata.name,OWNER:.metadata.ownerReferences[0].name
Expected output
replicaset.apps/nginx-rs created
pod/nginx-rs-8dttg condition met
pod/nginx-rs-h7jmt condition met
pod/nginx-rs-v6lsx condition met
NAME       DESIRED   CURRENT   READY   AGE
nginx-rs   3         3         3       2s
NAME             OWNER
nginx-rs-8dttg   nginx-rs
nginx-rs-h7jmt   nginx-rs
nginx-rs-v6lsx   nginx-rs
Delete one Pod
POD=$(kubectl get pods -l app=nginx-rs -o jsonpath='{.items[0].metadata.name}')
kubectl delete pod $POD
kubectl get pods -l app=nginx-rs
Expected output
pod "nginx-rs-8dttg" deleted from default namespace
NAME             READY   STATUS              RESTARTS   AGE
nginx-rs-g5hg7   0/1     ContainerCreating   0          1s
nginx-rs-h7jmt   1/1     Running             0          10s
nginx-rs-v6lsx   1/1     Running             0          10s
What just happened
  • The ReplicaSet compares desired (3) with actual (2) and creates a Pod from its template. That loop never stops.
  • Each Pod has an ownerReference pointing at the ReplicaSet. That's how Kubernetes knows what to clean up later.
  • Compare Module 3: a bare Pod you delete is gone forever. Here a replacement appears within seconds, with a new name and a new IP.
Checkpoint
Still 3 Pods — one of them is brand new.

Adoption and orphans

M4 slides 15, 17, 33 · Quiz Q3~6 min

Goal: Prove that a ReplicaSet counts every Pod that matches its selector — even ones it didn't create.

Run from: module4-lab/
Start a Pod by hand with the same label
kubectl run stray --image=nginx:1.28-alpine --labels=app=nginx-rs
sleep 3
kubectl get pods -l app=nginx-rs
kubectl get events --field-selector involvedObject.name=nginx-rs,reason=SuccessfulDelete -o custom-columns=REASON:.reason,MESSAGE:.message
Expected output
pod/stray created
NAME             READY   STATUS    RESTARTS   AGE
nginx-rs-g5hg7   1/1     Running   0          20s
nginx-rs-h7jmt   1/1     Running   0          28s
nginx-rs-v6lsx   1/1     Running   0          28s
REASON             MESSAGE
SuccessfulDelete   Deleted pod: stray
Delete only the ReplicaSet, then bring it back
kubectl delete rs nginx-rs --cascade=orphan
kubectl get pods -l app=nginx-rs -o custom-columns=NAME:.metadata.name,OWNER:.metadata.ownerReferences[0].name
kubectl apply -f nginx-rs.yaml
sleep 2
kubectl get pods -l app=nginx-rs -o custom-columns=NAME:.metadata.name,OWNER:.metadata.ownerReferences[0].name
Expected output
replicaset.apps "nginx-rs" deleted from default namespace
NAME             OWNER
nginx-rs-g5hg7   <none>
nginx-rs-h7jmt   <none>
nginx-rs-v6lsx   <none>
replicaset.apps/nginx-rs created
NAME             OWNER
nginx-rs-g5hg7   nginx-rs
nginx-rs-h7jmt   nginx-rs
nginx-rs-v6lsx   nginx-rs
Clean up — the Pods go with it
kubectl delete -f nginx-rs.yaml
sleep 3
kubectl get pods -l app=nginx-rs
Expected output
replicaset.apps "nginx-rs" deleted from default namespace
No resources found in default namespace.
What just happened
  • The stray Pod matched app=nginx-rs, so the ReplicaSet adopted it. Now it had 4 Pods but wanted 3 — so it deleted one. Your debug Pod vanished without an error (Quiz Q3).
  • Lesson: never reuse a controller's labels for your own Pods. Use unique labels like app=checkout-debug.
  • --cascade=orphan deletes the owner but keeps the Pods running with no owner. The new ReplicaSet adopted all 3 — no restarts. Teams use this to change a selector or migrate between controllers.
  • The default (--cascade=background) deletes the Pods too, as you saw in the last command.
Checkpoint
stray was deleted by the ReplicaSet, and the orphans were adopted again.

A production-ready Deployment

M4 slides 18–22, 34 · Quiz Q9~8 min

Goal: Write a Deployment with the fields production teams actually use, check it with both dry-runs, then apply it.

Run from: module4-lab/
Creates: deployment.yaml
cat > deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
  annotations:
    kubernetes.io/change-cause: "Initial deploy nginx 1.28-alpine"
spec:
  replicas: 4
  revisionHistoryLimit: 5        # keep 5 old ReplicaSets for rollback
  progressDeadlineSeconds: 60    # a rollout stuck for 60 s is marked failed
  selector:
    matchLabels:
      app: nginx
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                # at most 1 extra Pod during a rollout
      maxUnavailable: 0          # never drop below 4 ready Pods
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.28-alpine
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: 50m
              memory: 32Mi
            limits:
              cpu: 200m
              memory: 128Mi
          readinessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
EOF
Check it first — nothing is saved
kubectl apply --dry-run=client -f deployment.yaml
kubectl apply --dry-run=server -f deployment.yaml
Expected output
deployment.apps/nginx-deployment created (dry run)
deployment.apps/nginx-deployment created (server dry run)
Terminal
kubectl apply -f deployment.yaml
kubectl rollout status deployment/nginx-deployment --timeout=120s
kubectl get deploy,rs -l app=nginx
kubectl get pods -l app=nginx --show-labels
Expected output
deployment.apps/nginx-deployment created
Waiting for deployment "nginx-deployment" rollout to finish: 0 of 4 updated replicas are available...
Waiting for deployment "nginx-deployment" rollout to finish: 1 of 4 updated replicas are available...
Waiting for deployment "nginx-deployment" rollout to finish: 2 of 4 updated replicas are available...
Waiting for deployment "nginx-deployment" rollout to finish: 3 of 4 updated replicas are available...
deployment "nginx-deployment" successfully rolled out

What just happened
  • Recreate stops all old Pods first, then starts the new ones. Every X is a user getting an error. Your count will differ — but it won't be zero.

RollingUpdate — and the last few failed requests

M4B slides 22–23, 32 · Quiz Q5, Q6~8 min

Goal: Switch back to RollingUpdate, measure again, then add a preStop hook and reach zero failed requests.

Run from: module4-lab/
RollingUpdate, surge 1, unavailable 0
kubectl patch deployment web --type=merge -p '{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":1,"maxUnavailable":0}}}}'
kubectl set env deployment/web GREETING="Hello from v3" && ./probe.sh
kubectl rollout status deployment/web --timeout=60s
Expected output
deployment.apps/web patched
deployment.apps/web env updated
.......................X..X....................X............
ok=57 failed=3
deployment "web" successfully rolled out

Much better — but maybe not perfect. Each old Pod gets SIGTERM and stops listening at the same moment it is removed from the Service. For a second, some nodes still send it traffic. The fix is a short pause before shutdown:

Add a preStop sleep (this is itself a rollout) — then wait until old Pods are really gone
kubectl patch deployment web -p '{"spec":{"template":{"spec":{"containers":[{"name":"api","lifecycle":{"preStop":{"sleep":{"seconds":5}}}}]}}}}'
kubectl rollout status deployment/web --timeout=120s
kubectl get deploy web -o jsonpath='terminatingReplicas={.status.terminatingReplicas}{"\n"}'
until [ "$(kubectl get deploy web -o jsonpath='{.status.terminatingReplicas}')" = "0" ]; do sleep 1; done
Expected output
deployment.apps/web patched
Waiting for deployment "web" rollout to finish: 1 out of 3 new replicas have been updated...
...
deployment "web" successfully rolled out
terminatingReplicas=1
Measure again
kubectl set env deployment/web GREETING="Hello from v4" && ./probe.sh
kubectl rollout status deployment/web --timeout=120s
Expected output
deployment.apps/web env updated
............................................................
ok=60 failed=0
deployment "web" successfully rolled out
What just happened
  • maxSurge: 1, maxUnavailable: 0 with 3 replicas: at most 4 Pods, always 3 ready. Capacity never dips (Quiz Q5 uses different numbers — do the math).
  • The remaining failures came from the shutdown race, not from capacity. preStop: sleep: 5 keeps the old Pod serving for 5 s while every node removes it from the Service. Then SIGTERM arrives and the app shuts down gracefully (Quiz Q6).
  • "Successfully rolled out" came before the old Pods finished shutting down: terminatingReplicas was still 1 (you may see 1–3). That field is new in v1.37 (beta, on by default). We wait for it to reach 0 so the next measurement starts clean.
  • sleep is a built-in preStop action — no sleep binary needed in the image. The Pod's terminationGracePeriodSeconds (default 30 s) must be longer than the sleep.
  • Your numbers may differ from run to run. If you saw 0 failures in the first measurement, run it again — the race is timing-dependent. With preStop it stays at 0.

In a real repo, put the hook in web.yaml instead of patching:

web.yaml — the declarative version
      containers:
        - name: api
          lifecycle:
            preStop:
              sleep:
                seconds: 5
Checkpoint
The last probe shows ok=60 failed=0.

Headless and ExternalName Services

Goal: Meet the two Service kinds that don't load-balance: a headless Service that returns Pod IPs, and an ExternalName Service that is only a DNS alias.

Run from: module4-lab/
Creates: db-headless.yaml — a StatefulSet and its headless Service
cat > db-headless.yaml <<'EOF'
apiVersion: v1
kind: Service
metadata:
  name: db
spec:
  clusterIP: None          # headless: no virtual IP, DNS returns Pod IPs
  selector:
    app: db
  ports:
    - port: 80

  name: db

What just happened
  • web is a normal ClusterIP Service: DNS returns one virtual IP, and kube-proxy spreads the traffic.
  • db has clusterIP: None — it's headless. There is no virtual IP; DNS returns the IP of every ready Pod, and the client chooses.
  • With a StatefulSet, each Pod also gets its own stable name: db-0.db, db-1.db. Databases use this so replicas can find the primary by name.
  • We use full names with busybox's nslookup to keep the output short. Apps can use the short names — wget http://db-0.db just worked.

What just happened
  • An ExternalName Service has no Pods, no IP and no ports. DNS simply answers with a CNAME: "partner-api is really web.default.svc.cluster.local".
  • In real life it points outside the cluster — a managed database or a partner API. Apps call partner-api; when the address changes, you edit one Service, not every app.
  • It is only DNS. There is no proxying, so HTTPS certificates and HTTP Host headers still see the original name. Some APIs reject that — test before you rely on it.

Troubleshooting

Error from server (Forbidden): … exceeded quota or must specify limits.cpu
A ResourceQuota is active in that namespace. Add requests and limits to the Pod, or add a LimitRange with defaults (Steps 3–4).
A Deployment says created but stays at READY 0/N
Run kubectl describe deploy <name> and kubectl get events. Look for ReplicaFailure / FailedCreate (Step 4).
No resources found in … namespace but you expected Pods
You're in another namespace. Check kubectl config view --minify -o jsonpath='{..namespace}' and switch back with kubectl config set-context --current --namespace=default.
kubectl rollout status hangs or ends with exceeded its progress deadline
The new Pods never become ready. Check kubectl get pods and describe the new Pod. Fix the YAML or run kubectl rollout undo (Steps 11–12).
Pods stuck in ImagePullBackOff for module1-demo-api
The image isn't inside the kind nodes. Run kind load docker-image module1-demo-api:1.0.0 --name lab (Step 14). The YAML uses imagePullPolicy: IfNotPresent.
EXTERNAL-IP stays <pending>
cloud-provider-kind isn't running. Start it in a second terminal and keep it open (Step 16).
go: command not found when installing cloud-provider-kind
Install Go from go.dev, or download the release binary for your OS from the project's GitHub releases page and put it on your PATH.
spec.strategy.rollingUpdate: Forbidden
You switched to Recreate but the old rollingUpdate block is still there. Add "rollingUpdate":null to the same patch (Step 18).
./probe.sh: Permission denied or pods "client" not found
Run chmod +x probe.sh. The probe uses the client Pod from Step 14 — create it again if you deleted it.
curl to the NodePort or LoadBalancer IP hangs from your laptop
On Docker Desktop, container IPs aren't reachable from the host. Call it from a node: docker exec lab-control-plane curl -s http://<ip>:<port>.
kind load fails with ctr: content digest sha256:… not found
Docker 29 keeps images in its containerd image store: it downloads only your platform, but docker save still lists all of them, and kind's import looks for every one. Save just your platform and load the archive — that's what the pre-load commands at the top of this page do: docker save --platform "$(docker version --format '{{.Server.Os}}/{{.Server.Arch}}')" -o image.tar IMAGE then kind load image-archive image.tar --name lab. Images you built yourself (like module1-demo-api) load fine with kind load docker-image.
ERROR: unknown containerd config version: 4 from kind
Your kind binary is older than the node image. Install kind v0.33 or newer (Module 2, Step 1) and run kind version to check.
